# AWS アーキテクチャ設計

要件から論理構成を作り、比較可能な判断を経て AWS の物理構成へ落とし込む。

「推奨」「任意」「例外」と明記した項目以外は必須とする。

## 設計の順序

### 必須

- 最初に利用者、外部システム、信頼境界、システム境界を示す。
- 次に処理、データ、メッセージ、外部連携の責務と流れを論理構成として示す。
- 論理構成の後で AWS サービス、ネットワーク、リソース間接続を決める。
- 正常系だけでなく、失敗、再試行、重複、タイムアウト、復旧の流れを示す。
- インターネット、他アカウント、他リージョン、社内ネットワークとの境界を明示する。

## サービス選定

### 必須

- サービス名から検討を始めず、処理特性、データ特性、非機能要件、運用体制を先に確認する。
- 現在の要件を満たす候補だけでなく、制限、失敗時の挙動、移行と撤退の方法を確認する。
- AWS のクォータ、対応リージョン、機能制限、料金条件は公式情報で確認する。
- `reference/service-selection.md` の候補を採用理由として使わず、案件の要件で判断する。

### 推奨

- 運用チームが保守できる範囲で、管理対象を減らせるサービスを優先する。
- 将来の可能性だけを理由に、現在の要件を超える複雑性を持ち込まない。

## 候補比較

### 必須

- アーキテクチャ上重要な判断では、採用案と少なくとも 1 つの現実的な代替案を比較する。
- 比較軸には、要件適合、セキュリティ、信頼性、性能、運用、費用、移行、チーム能力を含める。
- 比較できない項目は推測で評価せず、未決事項または検証項目にする。
- 採用しない案について、案件の条件では何が合わないかを記録する。

重要な判断には、コンピュート、主要データストア、同期・非同期、公開境界、認証、復旧方式、リージョン構成を含む。

## ADR

### 必須

- 重要な判断を ADR に記録する。
- ADR に状態、背景、関連要件、候補、判断、理由、影響、検証、見直し条件を含める。
- 承認済み ADR の結論を直接書き換えない。変更時は新しい ADR を作り、置き換え関係を残す。
- 実装と構成図から ADR を辿れるようにする。

## トレーサビリティ

### 必須

- 主要な要件を、ADR、AWS リソース、統制、試験へ紐付ける。
- 要件に紐付かないリソースには、共通統制、運用、移行などの目的を記録する。
- 要件変更時に影響する設計、IaC、テスト、Runbook を特定できるようにする。

## Gate 2

### 必須

次を満たすまで設計完了にしない。

- すべての必須要件に、設計上の対応または承認済み例外がある。
- 論理構成と AWS 物理構成が分けて記録されている。
- 重要な設計判断に ADR と代替案がある。
- データフロー、信頼境界、権限境界、障害時の流れが分かる。
- セキュリティ、信頼性、運用、費用のレビューがある。
- 検証方法と必要な証跡が決まっている。
- 設計の承認者が内容を確認している。

## 例外

- 置き換え可能な軽微な実装詳細は ADR を省いてよい。要件、公開境界、権限、データ、復旧、継続費用へ影響する判断は省かない。
