# AWS 共通技術標準

AWS の構成に共通して適用する、アカウント、権限、ネットワーク、データ、信頼性、性能、運用、費用の基準を定める。

「推奨」「任意」「例外」と明記した項目以外は必須とする。

## アカウントと基盤

### 必須

- 本番と非本番の分離方法を明示する。同じアカウントへ置く場合は、理由、影響範囲、補完策を記録する。
- 管理用アカウントへ一般のワークロードを置かない。
- 人の管理者アクセスは SSO、MFA、短期認証情報を基本とし、長期アクセスキーを原則として発行しない。
- 利用できるアカウントとリージョンを明示し、意図しない場所へのデプロイを検査する。
- Owner、Environment、Project、費用管理に必要なタグを定め、対応するリソースへ付ける。
- 監査ログの保存先、閲覧権限、保持期間、改ざん・削除への保護を決める。

## 権限

### 必須

- 実行主体ごとにロールを分け、必要な Action、Resource、Condition だけを許可する。
- Action または Resource に `*` を使う場合は、理由、影響、縮小できない根拠を記録する。
- デプロイ権限とアプリケーション実行権限を分ける。
- 他アカウントから引き受けられるロールは、信頼先と条件を名指しする。
- IAM とリソースポリシーの外部公開範囲を検査する。
- 権限拡大を含む差分は、セキュリティ観点の承認対象にする。

## ネットワーク

### 必須

- 外部公開が必要な入口だけを列挙し、その他のリソースを公開しない。
- DB と内部データストアは原則としてプライベートアクセスに限定する。
- セキュリティグループの Source、Destination、Port、Protocol を必要最小限にする。
- インバウンドだけでなく、アウトバウンドと名前解決の経路も設計する。
- NAT、VPC Endpoint、直接接続などの外向き経路を、通信要件、運用、費用から比較する。
- VPC を使う場合は、CIDR の重複、将来接続、AZ 間・リージョン間通信を確認する。
- 公開経路、信頼境界、暗号化区間を構成図へ示す。

### 推奨

- 計算資源は、外部公開が必要な入口を除き、パブリック IP を持たない場所へ置く。

## データと秘密情報

### 必須

- データを公開、内部、機密、規制対象などの承認済み分類へ割り当てる。
- データ分類ごとに、保存先、アクセス、暗号化、保持、削除、監査の方法を決める。
- 保存時と通信時の暗号化を有効にし、必要な場合は鍵の所有者、ローテーション、復旧方法を決める。
- S3 などの意図しないパブリック公開を防止し、ポリシーと ACL の両方を確認する。
- 秘密値をコード、IaC、ログ、例外、デプロイ引数へ入れない。
- 秘密情報は保管先だけを IaC で作り、実値を別の承認された経路で投入する。
- データを持つリソースは、削除・置換時の保持と復元方法を明示する。
- バックアップの存在だけで合格にせず、要件に基づく復元試験を行う。

## セキュリティ

### 必須

- 認証と認可を分け、利用者、管理者、サービス間通信の境界ごとに設計する。
- 個人情報・機密情報をログへ出さず、必要な識別子はマスキングする。
- CloudTrail などの監査イベントと、セキュリティ上重要な操作を収集する。
- OS、コンテナ、ライブラリ、IaC の脆弱性を検出し、対応責任者と期限を決める。
- 外部公開 API では、認証、入力検証、レート制限、攻撃対策の必要性を脅威から評価する。
- セキュリティ検出サービスだけで、業務ロジックの認可が正しいと判断しない。
- インシデント時の封じ込め、証跡保全、連絡先、復旧手順を決める。

## 信頼性と復旧

### 必須

- AZ、リージョン、DB、キュー、外部 API、証明書、DNS、手作業を含めて単一障害点を確認する。
- RTO と RPO に対応するバックアップ、冗長化、復旧方式を選び、試験方法を決める。
- Multi-AZ とマルチリージョンを区別し、後者は明確な要件がある場合に評価する。
- 外部呼び出しに接続・読み取りタイムアウトを設定する。
- 再試行には回数上限、間隔、バックオフ、ジッターを設け、負荷増幅を防ぐ。
- 重複イベントや再実行が起こる経路では、冪等性の方法を決める。
- 非同期処理では、配信保証、順序、重複、可視性タイムアウト、DLQ、再処理、滞留監視を設計する。
- サービスクォータと、上限へ近づいた場合の検知・対応を確認する。
- デプロイ失敗時のロールバックまたはロールフォワードを決める。
- 依存先が停止した場合の縮退、保留、再処理、利用者への通知を決める。

## 性能

### 必須

- 通常時、ピーク時、成長時の負荷条件を要件から定義する。
- レイテンシ、処理量、同時実行、キュー滞留、接続数など、ボトルネックになり得る上限を確認する。
- キャッシュ、並列化、バッチ化を使う場合は、整合性、失効、再実行への影響を設計する。
- 性能要件は、IaC の設定だけで合格にせず、要件と同じ条件の試験で確認する。

## 監視と運用

### 必須

- ログを構造化し、時刻、環境、処理、相関 ID、結果を追跡できるようにする。
- エラー率、レイテンシ、処理量、滞留、停止を、要件と利用者影響から監視する。
- アラームには重要度、通知先、対応時間、Runbook、エスカレーション先を紐付ける。
- 通知を受けても行動できないアラームを作らない。
- ログ、メトリクス、トレースの保持期間と費用条件を決める。
- 定期処理と自動化には、最終成功時刻、失敗、未実行を検知する方法を設ける。
- 運用者が権限、依存先、復旧方法を確認できる Runbook を用意する。

## 費用と持続可能性

### 必須

- 費用を Compute、Database、Storage、Network、Observability、Security、Other に分ける。
- 通常時、ピーク時、成長時について、利用量、稼働時間、対象環境、料金条件を明示する。
- NAT、AZ 間、リージョン間、インターネット向けのデータ転送費用を確認する。
- 開発・検証環境、ログ、バックアップ、監視、セキュリティサービスも見積対象に含める。
- 費用の数値を推測せず、AWS の料金情報と承認済み利用量を使う。
- 予算と異常費用の監視方法、通知先、対応方法を決める。
- 常時課金されるリソースを追加する場合は、必要性と停止・縮小できる条件を示す。

### 推奨

- 非本番リソースは、利用しない時間に停止または削除できるようにする。
- 要件を満たす範囲で、過剰な容量、不要なデータ保持、不要な通信を減らす。

## 例外

- Lambda などは、上の「ネットワーク」の推奨にかかわらず、一律に VPC へ置かない。VPC 内リソースへの接続、固定経路、組織統制などの要件がある場合に接続する。
- 短期の検証環境では一部の運用統制を省いてよい。ただし、本物の個人情報・機密情報を使用せず、期限、責任者、削除方法を決める。
