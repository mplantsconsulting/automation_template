# AWS 設計の自動化と承認

設計ルールを文章だけで終わらせず、静的検査、実行試験、専門家レビュー、承認へ割り当てる。

「推奨」「任意」「例外」と明記した項目以外は必須とする。

## 統制ルールの形式

### 必須

機械処理する統制には次を持たせる。

| 属性 | 内容 |
| --- | --- |
| `rule_id` | 変更しない一意な ID |
| `version` | ルールの版 |
| `title` | 人が読める名前 |
| `category` | security、network、reliability など |
| `severity` | critical、high、medium、low |
| `applicability` | 対象環境、リソース、条件 |
| `expected` | 合格となる状態 |
| `verification` | 判定方法と対象 |
| `enforcement` | 失敗時の処理 |
| `rationale` | 必要な理由 |
| `exception` | 例外の可否と条件 |
| `evidence` | 合格を示す証跡 |

- ルール ID を再利用しない。
- 適用条件を明示し、対象外を合格として数えない。
- 自動判定できない内容を、設定値だけで合格にしない。
- 検査コードには合格例、違反例、対象外のテストを用意する。
- ツール固有の式と、人が読む理由を分けて記録する。

## 検証の分類

### 必須

| 種類 | 判定方法 | 例 |
| --- | --- | --- |
| Type A | 設定値を静的または継続的に検査 | 公開設定、暗号化、IAM、削除保護 |
| Type B | 実際に動かして検査 | 性能、復旧時間、フェイルオーバー、バッチ完了 |
| Type C | 専門的判断と承認 | 要件適合、過剰設計、業務リスク、例外受容 |

- Type A は CloudFormation Guard、IaC 静的解析、AWS Config など、対象に合う決定的な検査へ割り当てる。
- Type B は実行条件、期待結果、証跡、実施環境を決める。
- Type C は判断する役割、確認事項、承認記録を決める。
- AI のレビュー結果だけを Type A または Type B の合格証跡にしない。

## 重大度と処理

### 必須

- `critical` はデプロイを止め、例外可能かどうかをルールごとに定める。
- `high` は原則としてデプロイを止め、承認済み例外がある場合だけ進める。
- `medium` はレビューを要求し、対応または受容理由を記録する。
- `low` は改善候補として記録し、放置ではなく追跡方法を決める。
- 重大度はサービス名ではなく、機密性、完全性、可用性、費用、影響範囲から決める。

## 証跡

### 必須

- 要件ごとに、どの設計、統制、試験結果が合格を支えるかを記録する。
- 検証結果に実行日時、対象環境、対象の版、実行条件、結果を含める。
- 手動レビューには承認者、判断、未解決事項を含める。
- 古い環境や古い IaC に対する結果を、現在の構成の証跡として再利用しない。

## 検証ゲート

### 必須

| Gate | 確認内容 | 失敗時 |
| --- | --- | --- |
| 要件 | 形式、必須情報、仮定と未決事項 | 設計承認を止める |
| 設計 | 必須要件との対応、ADR、リスク、検証計画 | IaC 生成を止める |
| IaC | 構文、合成、Lint、単体テスト、静的解析 | マージを止める |
| 統制 | セキュリティ、公開範囲、暗号化、権限、保持 | 重大度に従って止める |
| 変更 | 差分、置換、削除、権限拡大、費用条件 | 人の承認を要求する |
| 実行試験 | 統合、性能、復旧、セキュリティ | 本番リリースを止める |
| 反映後 | ヘルスチェック、主要処理、監視 | ロールバック判断と通知 |

- PR では、影響する Gate をすべて実行する。
- 文書だけの変更でも、リンク、形式、ルールのテストを実行する。
- 検査をスキップする場合は、対象、理由、期限、承認者を記録する。
- 不安定な検査を再実行だけで通さない。

## 変更差分

### 必須

デプロイ前に次を表示する。

- 対象アカウント、リージョン、環境
- 作成、更新、置換、削除されるリソース
- IAM とリソースポリシーの権限拡大
- インターネット、他アカウント、他リージョンへの公開範囲
- データ、バックアップ、暗号鍵、秘密情報への影響
- 継続費用が増えるリソースと見積条件
- 実行順序、停止時間、ロールバック方法

削除、置換、権限拡大、外部公開を、通常の更新に埋もれさせない。

## 例外

### 必須

- 例外には一意な ID、対象ルール、対象リソース、理由、リスク、補完策、承認者、期限、解消タスクを付ける。
- 期限のない例外を作らない。
- 期限切れの例外は自動的に合格として扱わず、再審査する。
- 例外を許可しない統制を、ルール側で明示する。
- 補完策を実際に検証し、その証跡を例外へ紐付ける。
- 同じ例外が繰り返される場合は、個別例外ではなくルールまたは設計を見直す。

## デプロイ承認

### 必須

- AWS へ書き込む前に、差分と検証結果を利用者へ示して承認を得る。
- 本番、権限拡大、外部公開、データ削除・置換、暗号鍵、秘密情報、例外を含む変更は、明示的な承認なしに実行しない。
- 承認は対象の差分に対して取得し、承認後に差分が変わった場合は再承認を得る。
- 本番の前に、同じ IaC と手順を非本番で確認する。
- デプロイ後の確認とロールバック判断までを変更手順に含める。

## Gate 3

### 必須

次を満たすまで本番リリース可能としない。

- Gate 1 と Gate 2 が承認済みである。
- IaC の差分に不明な置換・削除がない。
- Type A の必須統制が合格している。
- 必要な Type B の試験が現在の版に対して合格している。
- Type C のレビューと例外が承認されている。
- 費用条件、監視、Runbook、ロールバック方法が確認されている。
- 本番変更の承認者が差分とリスクを確認している。

## 緊急対応

### 必須

- 緊急対応で通常の順序を短縮する場合も、対象、判断者、実施内容、検証結果を記録し、事後に省略した検証とレビューを行う。
