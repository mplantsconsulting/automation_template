# AGENTS.md

AWS アーキテクチャを設計、レビュー、実装するときの AI への指示です。

## 最初に読むもの

1. ルートの `rules/general.md`
2. ルートの `rules/git.md`
3. ルートの `rules/infra.md`
4. `aws/rules/requirements.md`
5. `aws/rules/architecture.md`
6. `aws/rules/engineering.md`
7. `aws/rules/automation.md`

AWS サービスの候補を検討するときだけ `aws/reference/service-selection.md` を読みます。
インフラの工数を見積もるときだけ `aws/reference/estimate-infra.md` を読みます。
参考情報を必須ルールとして扱いません。

## 守ること

- 数値、利用規模、可用性、RTO、RPO、予算、保存期間を推測で埋めない。
- 未確認の内容は `ASM` または未決事項として明示し、承認済み要件に混ぜない。
- AWS サービスを選ぶ前に、システム境界、責務、データフローを論理構成として示す。
- 重要な設計判断では、採用案だけでなく比較対象と採用しなかった理由を示す。
- 要件、ADR、AWS リソース、検証方法の対応関係を残す。
- セキュリティ、信頼性、運用、費用を、機能の実現とは別に確認する。
- IaC を生成する前に設計を提示し、利用者の承認を得る。
- AWS へ変更を加える前に、対象アカウント、リージョン、差分、削除・置換、権限拡大、公開範囲、継続費用を示し、承認を得る。
- 本番デプロイ、データの削除、権限拡大、外部公開、例外の承認を AI が決定しない。
- AWS 公式情報と現在のコード・設定が食い違う場合は、黙って一方を選ばず報告する。

## 実行手順

### 1. 要件を整理する

入力を `BR`、`FR`、`NFR`、`CON`、`ASM` に分類します。
不足事項を `open_questions` にまとめ、同じ段階の質問は 1 回にまとめます。
Gate 1 の条件を満たすまで、本番構成を確定した表現をしません。

### 2. 論理構成を作る

利用者、外部システム、システム境界、処理の責務、データ、同期・非同期の流れ、障害時の流れを示します。
この段階では AWS サービスを先に固定しません。

### 3. AWS 構成を比較する

要件に基づいて候補を絞り、重要な判断について比較表と ADR を作ります。
比較軸は、要件適合、セキュリティ、信頼性、性能、運用負担、費用、移行、チームの保守能力です。

### 4. 独立した観点でレビューする

次の観点ごとに、満たす要件、根拠、未解決事項を示します。

- セキュリティとデータ保護
- 信頼性、バックアップ、復旧
- 性能とクォータ
- 監視、障害対応、運用手順
- 通常時、ピーク時、成長時の費用条件

### 5. IaC と検証を作る

承認済み設計から IaC を作り、統制を Type A、Type B、Type C に分類します。
Type A は静的検査、Type B は実行試験、Type C は専門家レビューへ割り当てます。

### 6. 差分を示して承認を得る

デプロイ前に、変更、置換、削除、権限、公開範囲、費用、ロールバック方法を示します。
承認なしに AWS へ書き込みません。

### 7. デプロイ後を確認する

ヘルスチェック、アラーム、ログ、主要処理、ロールバック条件を確認し、結果を記録します。
設計と実環境の差は未解決事項として残さず、修正か承認済み例外にします。

## 出力の順序

1. 確定している要件
2. 仮定と制約
3. 未決事項
4. 論理構成
5. 候補比較と ADR
6. AWS 物理構成
7. リスクと統制
8. 検証計画
9. 承認が必要な事項

結論だけを出さず、要件から判断と検証まで辿れる形にします。
