# Git と Pull Request

履歴を追跡でき、常に安全にリリースできる状態を保つ。

「推奨」「任意」「例外」と明記した項目以外は必須とする。

## ブランチ

| ブランチ | 役割 | 変更方法 |
| --- | --- | --- |
| `main` | リリース済みで常にデプロイ可能 | `dev` から PR |
| `dev` | 次のリリース候補 | 作業ブランチから PR |
| 作業ブランチ | 1 つの目的の変更 | `dev` から作成して `dev` へ PR |

### 必須

- `main` と `dev` へ直接 push せず、CI が通った PR だけをマージする。
- 作業ブランチは `dev` の最新から切り、`type/短い説明` で命名する。
- 1 ブランチを 1 目的に絞り、マージ後に削除する。

### 推奨

- 作業ブランチは数日以内に終え、1 週間を超える場合は分割する。
- `dev` の取り込みは個人ブランチでは rebase、共有ブランチでは merge を使う。
- force push は自分だけのブランチで `--force-with-lease` を使う場合に限る。
- 緊急修正は `main` から `hotfix/` を切り、マージ後に `dev` へ反映する。

## コミット

### 必須

- 1 行目を `type: 要約` とし、`feat`、`fix`、`docs`、`refactor`、`test`、`chore` から選ぶ。
- 要約は 50 文字程度に収め、1 コミットを 1 変更にする。
- コミット前に差分を確認し、生成物、個人設定、デバッグ出力、秘密情報を除く。

### 推奨

- 本文には差分の説明ではなく変更理由を書き、関連する Issue や PR を記載する。
- WIP コミットは PR 前に意味のある単位へ整理する。

## Pull Request

### 必須

- タイトルをコミットと同じ `type: 要約` にし、末尾に対応するタスクの ID を `（TSK-000）` で付ける。
- 1 つの PR を 1 つのタスクに対応させる。
- 本文の 1 行目を `タスク: [<タスクID> <タスク名>](<タスクのURL>)` とし、その次を `## 目的` にする。
- タスク側にも PR を紐付け、どちらからでも辿れるようにする。
- `## 目的` に、何をなぜ変えるかを 1〜3 文の丁寧語で書く。
- 特に見てほしい箇所を 1〜3 件、理由とともに示す。
- 作業経緯、差分の言い換え、長いログ、CI が表示する情報、免責だけの文を書かない。
- レビュー指摘には対応内容を返答し、対応しない場合は理由を書く。
- マージ前にテスト、セキュリティ、エラー経路、不要コード、Lint、型、ビルドを確認する。

### 推奨

- 必要な場合だけ、対象ファイル、設計判断、確認結果、残る制約を追加する。
- 作業途中は Draft にし、レビュー可能になってから解除する。
- レビューは正しさ、読みやすさ、テスト、セキュリティ、既存ルールとの整合を見る。
- 指摘は問題と修正案を対で示し、必須か提案かを明記する。
- タスクのステータスを PR の状態に合わせる。レビュー依頼時にレビュー、マージ後に完了。
- PR が大きくなったらタスクを分け、PR も分ける。

## マージ

- 作業ブランチから `dev` へは squash merge を使う。
- `dev` から `main` へは merge commit を使う。
- 積み上げ PR は手前から merge commit で取り込み、後続 PR のベースを `dev` へ変更してからブランチを削除する。
- CI 成功、1 名以上の承認、コンフリクト解消をマージ条件にする。

## 例外

- 小規模または使い捨てのプロジェクトは `main` だけで運用してよいが、その方針を README に書く。
- 軽微な文書・設定変更は `dev` へ直接コミットしてよいが、`main` への直接 push は禁止する。
- 個人開発では PR を残したうえでセルフマージしてよい。
- 軽微な文書・設定変更ではタスクを作らなくてよい。その場合はタイトルのタスク ID と本文のタスク行を省く。
- タスク管理ツールを使っていないプロジェクトでは、タスクに関する項目を適用しない。
