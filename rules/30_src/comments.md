# コメントと docstring

| 項目 | 内容 |
| --- | --- |
| 対象 | すべてのソースコード内のコメント、docstring、TODO |
| レベル | 推奨 |
| 最終更新 | 2026-09-10 |

## 目的

コードと食い違ったコメントは、ないより有害である。読み手はコメントを信じて誤った理解をする。
一方で「なぜそうしたか」がどこにも書かれていないと、後から触る人は意図を推測するしかなく、必要な処理を消してしまう。
ここでは「コードで表せることはコードに任せ、コメントは理由だけを書く」ための基準を定める。

## ルール

### MUST

- コードを読めば分かること(何をしているか)をコメントに書かない。処理の内容は関数名・変数名で表す。
- コメントには「なぜ」を書く。仕様上の制約、回避策の理由、一見不要に見える処理の必要性など、コードから読み取れない背景を残す。
- 公開関数(他のモジュールから呼ばれる関数・メソッド・クラス)には docstring を書き、目的、引数、戻り値、発生する例外を記載する。
- コメントアウトしたコードを残さない。不要なコードは削除し、履歴は Git に任せる。
- コードを変更したら、関係するコメントと docstring も同じ PR で更新する。古くなったコメントは削除する。
- コメントの言語はプロジェクトで 1 つに統一する(日本語か英語)。1 つのリポジトリ内で混在させない。

### SHOULD

- `TODO` `FIXME` には担当者名か Issue 番号を付け、放置されない形にする。付けられない TODO は書かずに Issue を作る。
- 内部関数の docstring は、名前と引数で意図が伝わるなら省略してよい。伝わらないなら名前を見直す。
- 複雑な条件式や計算式には、式の意味を 1 行で説明するコメントを添えるか、意味を表す名前の変数に分ける。
- 外部仕様や参考資料に基づく実装には、その出典(仕様書名、URL、チケット番号)を書く。
- コメントは対象のコードの直前に置き、離れた場所やファイル末尾にまとめない。

### MAY

- モジュールやファイルの冒頭に、そのファイルの役割を 1〜3 行で書いてもよい。
- 一時的な回避策(workaround)には、解消条件(依存ライブラリの修正版リリースなど)を書いてもよい。

## Good / Bad 例

```text
# Bad: コードを日本語に翻訳しているだけ
i = i + 1  # i に 1 を足す
users = get_users()  # ユーザーを取得する

# Good: コードから読めない理由を書く
# 外部 API が 1 リクエスト 100 件までしか返さないため、ページングして取得する
users = fetch_all_users(page_size=100)
```

```text
# Bad: 消した理由も分からないコードが残っている
# old_total = calc_total_v1(items)
# if old_total > 1000:
#     apply_discount(items)
total = calc_total(items)

# Good: 不要なコードは削除する。必要なら Git 履歴を参照する
total = calc_total(items)
```

```text
# Bad: 誰がいつやるか分からない TODO
# TODO: あとで直す

# Good: 担当か Issue 番号があり、追跡できる
# TODO(#123): 締め日が月末以外のケースに対応する
```

```text
# Good: 公開関数の docstring。目的、引数、戻り値、例外がそろっている
def load_orders(path, since):
    """指定日以降の注文を CSV から読み込む。

    引数:
        path: 注文 CSV のパス
        since: この日付以降の注文だけを返す
    戻り値:
        Order のリスト。該当がなければ空リスト
    例外:
        FileNotFoundError: path が存在しない
        InvalidFormat: CSV のヘッダーが期待と異なる
    """
```

## チェックリスト

- [ ] コメントが「何をしているか」ではなく「なぜ」を説明しているか
- [ ] 名前を変えればコメントが不要になる箇所がないか
- [ ] 公開関数に目的、引数、戻り値、例外を含む docstring があるか
- [ ] コメントアウトされたコードが残っていないか
- [ ] 変更したコードに関係するコメントと docstring が更新されているか
- [ ] `TODO` に担当者か Issue 番号が付いているか
- [ ] コメントの言語がプロジェクトの統一言語と一致しているか

## 例外

- 自動生成されたコード(スキーマから生成したクライアント、マイグレーションなど)のコメントは生成ツールの出力に従い、手で直さない。
- ライセンス表記や著作権表示など、法的に必要なコメントはこのルールの対象外とし、プロジェクトの定めた形式で書く。
