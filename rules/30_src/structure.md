# ディレクトリ構成

| 項目 | 内容 |
| --- | --- |
| 対象 | `src/` 配下のすべてのソースコードと、それに付随する `tests/` `scripts/` `config/` |
| レベル | 必須 |
| 最終更新 | 2026-09-10 |

## 目的

ファイルの置き場所に規則がないと、コードを探す時間と「どこに書くか」を迷う時間が積み上がる。
責務の境界が曖昧なまま依存が絡み合うと、1 か所の修正が無関係な機能を壊し、テストも書けなくなる。
ここでは責務ごとにディレクトリを分け、依存の向きを一方向に保つための構成を定める。

## ルール

### MUST

- 入口(`main` / `cli` / `app` など)は薄く保つ。引数の受け取りと処理の呼び出しだけを書き、ロジックは書かない。
- `src/` 配下は責務ごとにディレクトリを分ける。最低限、入出力層、ビジネスロジック、外部連携、共通ユーティリティを混在させない。
- 依存は外側から内側へ一方向にする。ビジネスロジックが入出力層や外部連携の実装を直接参照してはならない。
- 循環依存を作らない。A が B を参照し B が A を参照する構造はレビューで差し戻す。
- テストは `tests/` に置き、`src/` と同じディレクトリ構造でミラーする。
- `util` `common` `misc` のような、何でも入る名前のディレクトリやファイルを作らない。共通処理は用途を表す名前(`date_format` `retry` など)で置く。

### SHOULD

- 1 ファイルが 300〜500 行を超えたら分割を検討する。行数そのものより「複数の責務が混ざっていないか」で判断する。
- 運用・保守用のスクリプトは `scripts/` に置き、`src/` に混ぜない。
- 設定値は `config/` か環境変数で管理し、ソースコード内に散らさない。
- ディレクトリ名は複数形か機能名で統一し、プロジェクト内で表記を揺らさない。
- 外部サービスへの接続(API、DB、ファイル、メール)は外部連携層に集約し、差し替え可能にする。

### MAY

- 小規模なプロジェクトでは層を 2〜3 個に減らしてよい。ただし入口を薄く保ち、外部連携を分ける点は維持する。
- 機能単位(ドメイン単位)でディレクトリを切り、その中で層を分ける構成にしてもよい。

## Good / Bad 例

```text
# Bad: 入口にロジックが集まり、util に何でも入っている
src/
├── main.py            # 引数解析、API 呼び出し、集計、CSV 出力がすべて 800 行
└── util.py            # 日付変換、リトライ、DB 接続、文字列整形が同居

# Good: 責務ごとに分け、入口は呼び出しだけ
src/
├── main.py            # 引数を受け取り、services を呼ぶだけ
├── io/                # 入出力層(CLI 引数、ファイル読み書き、画面表示)
│   ├── cli.py
│   └── csv_writer.py
├── services/          # ビジネスロジック(集計、判定、変換)
│   └── monthly_report.py
├── clients/           # 外部連携(API、DB、メール)
│   ├── sales_api.py
│   └── mail_sender.py
└── shared/            # 用途が明確な共通処理
    ├── date_format.py
    └── retry.py
tests/
├── io/
│   └── test_csv_writer.py
├── services/
│   └── test_monthly_report.py
└── clients/
    └── test_sales_api.py
scripts/               # 運用スクリプト(初期データ投入、バックアップなど)
config/                # 環境ごとの設定ファイル
```

```text
# Bad: ビジネスロジックが外部連携の実装に直接依存している
services/monthly_report.py
    import clients.sales_api        # 内側が外側を参照
    data = sales_api.fetch_with_http(...)

# Good: 内側は抽象(インターフェース)だけを知り、実装は外側から渡す
services/monthly_report.py
    def build(fetch_sales):          # 取得手段は引数で受け取る
        data = fetch_sales(...)
main.py
    build(fetch_sales=sales_api.fetch)
```

## チェックリスト

- [ ] 入口ファイルにビジネスロジックが書かれていないか
- [ ] 新しいファイルは責務に合ったディレクトリに置かれているか
- [ ] ビジネスロジックが入出力層や外部連携の実装を直接参照していないか
- [ ] 循環依存が発生していないか
- [ ] テストファイルは `tests/` に `src/` と同じ構造で置かれているか
- [ ] `util` のような曖昧な名前のディレクトリやファイルを追加していないか
- [ ] 500 行を超えるファイルを追加・拡張していないか

## 例外

- 使い捨てのスクリプト(1 回実行して破棄するもの)は層を分けなくてよい。ただし `scripts/` に置き、使い捨てであることをファイル冒頭に書く。
- フレームワークがディレクトリ構成を規定している場合(Web フレームワークの規約など)は、その規約を優先する。ただし依存の向きと循環依存禁止は維持する。
