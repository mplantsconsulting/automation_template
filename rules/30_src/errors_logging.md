# エラー設計とログ

| 項目 | 内容 |
| --- | --- |
| 対象 | すべてのソースコードにおける例外処理、再試行、ログ出力 |
| レベル | 必須 |
| 最終更新 | 2026-09-10 |

## 目的

例外を握りつぶすと、障害が起きても気づけず、気づいたときには原因を追う手がかりが残っていない。
文脈のないエラーメッセージや秘密情報を含むログは、調査を遅らせるか、それ自体が事故になる。
ここでは「失敗は見える形で残し、調査に必要な情報だけをログに出す」ための基準を定める。

## ルール

### MUST

- 例外を握りつぶさない。捕まえて何もしない、あるいはログだけ出して続行する書き方は禁止する。
- 例外は処理できる場所でだけ捕まえる。処理できないなら捕まえずに上位へ伝える。
- 業務エラー(入力不備、対象なし、権限なしなど想定内の失敗)と予期しないエラー(バグ、外部障害)を区別し、業務エラーは専用の例外型で表す。
- エラーメッセージには文脈を含める。「何を」「何で」「どうなったか」が読めるようにし、原因調査に必要な識別子(ID、ファイル名など)を添える。
- ログにパスワード、トークン、API キー、個人情報を出さない。マスクするか出力対象から外す。
- `print` などのデバッグ出力をコミットに残さない。出力はすべてログ機構を通す。

### SHOULD

- 再試行は冪等な操作(何度実行しても結果が同じ)にだけ行う。再試行する場合は最大回数と間隔(指数バックオフなど)を決めて明示する。
- ログレベルは次のように使い分ける。DEBUG は開発時の詳細、INFO は正常な処理の節目、WARNING は続行できるが注意が要る事象、ERROR は処理が失敗し対応が必要な事象。
- ログは構造化する(キー=値、または JSON)。自由文にせず、検索や集計ができる形にする。
- 1 つのリクエストや実行を追跡できるよう、相関 ID(リクエスト ID、実行 ID)をすべてのログに含める。
- 例外を別の例外に変換するときは、元の例外を原因として保持し、スタックトレースを失わない。
- 同じ失敗を複数の層で重複してログに出さない。ログは最終的に処理した場所で 1 回出す。

### MAY

- 外部連携の呼び出しは、開始と終了(所要時間、結果)を INFO で記録してもよい。
- 利用者向けのメッセージと調査用のログメッセージを分けてもよい。利用者には対処法を、ログには技術的な詳細を出す。

## Good / Bad 例

```text
# Bad: 握りつぶして続行。失敗したことが誰にも分からない
try:
    upload(file)
except Exception:
    pass

# Good: 処理できないなら伝える。処理するなら文脈を残す
try:
    upload(file)
except NetworkError as e:
    raise UploadFailed(f"ファイル {file.name} のアップロードに失敗: 接続先 {host}") from e
```

```text
# Bad: 文脈がなく、自由文で、秘密情報が含まれる
log.error("失敗しました")
log.info(f"ログイン: user={name} password={password}")

# Good: 構造化し、文脈と相関 ID を含め、秘密情報は出さない
log.error("注文の確定に失敗", order_id=order.id, reason="在庫不足", request_id=req_id)
log.info("ログイン成功", user_id=user.id, request_id=req_id)
```

```text
# Bad: 非冪等な操作を無制限に再試行
while True:
    try:
        charge_card(amount)   # 成功しても再試行されると二重課金
        break
    except Exception:
        continue

# Good: 冪等な操作だけ、回数と間隔を決めて再試行
fetch_with_retry(url, max_attempts=3, backoff_seconds=[1, 2, 4])
```

## チェックリスト

- [ ] 例外を捕まえて何もしていない箇所がないか
- [ ] 例外を捕まえている場所で、本当にその失敗を処理できるか
- [ ] 業務エラーが専用の例外型で表されているか
- [ ] エラーメッセージから「何を、何で、どうなったか」が読めるか
- [ ] 再試行している操作は冪等か。最大回数と間隔が決まっているか
- [ ] ログレベルが事象の重大さと一致しているか
- [ ] ログに秘密情報や個人情報が含まれていないか
- [ ] `print` などのデバッグ出力が残っていないか
- [ ] ログに相関 ID が含まれているか

## 例外

- プログラムの最上位(入口)では、想定外の例外を 1 か所で捕まえて ERROR ログを出し、適切な終了コードで終了してよい。これは握りつぶしではない。
- 使い捨てのスクリプト(1 回実行して破棄するもの)は構造化ログや相関 ID を省いてよい。ただし秘密情報を出さない点は維持する。
