# CI パイプライン

| 項目 | 内容 |
| --- | --- |
| 対象 | CI の設定ファイルと、それを変更・運用するすべての人 |
| レベル | 必須 |
| 最終更新 | 2026-09-10 |

## 目的

CI がないと「自分の環境では動く」コードがそのままマージされ、壊れたことに気づくのは次に触った人になる。
CI があっても遅い・赤いまま放置されると、誰も結果を見なくなり、存在しないのと同じになる。
ここでは PR ごとに最低限回す検証と、CI を信頼できる状態に保つための運用を定める。

## ルール

### MUST

- すべての PR で Lint、テスト、ビルド(ビルド工程があるプロジェクトの場合)を CI で自動実行する。
- `dev` と `main` へのマージ条件に CI の成功を含める。CI が失敗している PR はマージしない。
- `dev` や `main` の CI が失敗したら、他の作業より優先して直す。直せない場合は原因のコミットを revert する。
- API キー、トークン、パスワードなどの秘密情報は CI の Secrets 機能で管理し、設定ファイルやログに平文で出さない。
- 依存ライブラリはロックファイルで固定し、CI ではロックファイルどおりにインストールする。CI 実行のたびにバージョンが変わる状態にしない。
- CI の設定ファイルもコードと同様にレビューする。CI 設定だけの変更でも PR を作る。

### SHOULD

- CI は 1 回 10 分以内に完了することを目標にする。超える場合はジョブの並列化、テストの分割、キャッシュの活用を検討する。
- 依存ライブラリのインストール結果をキャッシュし、毎回ゼロからインストールしない。キャッシュキーにはロックファイルのハッシュを使う。
- デプロイは `main` へのマージ後に行い、「自動デプロイ」か「手動承認後にデプロイ」かをプロジェクトで決めて README に書く。
- CI で実行するコマンドはローカルでも同じコマンドで実行できるようにする(例: `make test`、`npm test`)。CI 専用の手順を作らない。
- テストが不安定(実行ごとに結果が変わる)なら、再実行で通すのではなく原因を直す。直せない間はそのテストを一時的に除外し、Issue を作る。

### MAY

- PR ごとにプレビュー環境を自動作成してもよい。
- 定期実行(夜間など)で、依存ライブラリの脆弱性チェックや長時間テストを別ジョブとして回してもよい。

## Good / Bad 例

```text
# Bad: 秘密情報を設定ファイルに直接書き、ログにも出る
env:
  API_KEY: "sk-live-abc123..."
run: echo "Using key $API_KEY" && ./deploy

# Good: Secrets から渡し、値はログに出さない
env:
  API_KEY: ${{ secrets.API_KEY }}    # GitHub Actions の例
run: ./deploy
```

```text
# Bad: 依存を毎回最新で取り、実行ごとに結果が変わる
run: pip install requests pandas

# Good: ロックファイルで固定し、キャッシュする
cache:
  key: deps-${{ hashFiles('requirements.lock') }}
run: pip install -r requirements.lock
```

```text
# Bad: dev が赤いまま新機能の PR が積まれる
main: ✖ test failed (3 日前から)
PR #12: 新機能 A   PR #13: 新機能 B

# Good: dev の修正を最優先し、通ってから PR を進める
main: ✖ → PR #14 "fix: 失敗テストの修正" をマージ → main: ✔
```

## チェックリスト

- [ ] PR ごとに Lint、テスト、ビルドが CI で実行されるか
- [ ] CI 成功が `dev` と `main` へのマージ条件になっているか
- [ ] 秘密情報が Secrets 機能で管理され、ログに出ていないか
- [ ] ロックファイルがリポジトリにあり、CI がそれを使ってインストールしているか
- [ ] CI の実行時間が 10 分以内か。超えている場合は改善の Issue があるか
- [ ] デプロイの方針(自動 / 手動承認)が README に書かれているか
- [ ] CI 設定の変更が PR でレビューされているか

## 例外

- テストが 1 つもない立ち上げ直後のプロジェクトでは、テストジョブを省いてよい。ただし Lint とビルドは最初から回し、最初のテスト追加時にジョブを追加する。
- ドキュメントのみの変更(Markdown、画像)では、テストとビルドをスキップしてよい。Lint(markdownlint など)は実行する。
