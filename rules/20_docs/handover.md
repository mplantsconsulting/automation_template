# 引き継ぎ資料の書き方

| 項目 | 内容 |
| --- | --- |
| 対象 | 担当交代、長期離脱、外部委託の終了時に作る HANDOVER.md |
| レベル | 必須 |
| 最終更新 | 2026-09-10 |

## 目的

引き継ぎ資料がないと、前任者の退任後に「なぜこうなっているか」を誰も答えられなくなる。
結果として触れないコードが増え、障害時の復旧が遅れ、同じ失敗を繰り返す。
初見の人が資料だけで作業を再開できる状態にすることがこのルールの目的である。

## ルール

### MUST

- 資料はリポジトリのルートに `HANDOVER.md` として置き、README からリンクする。
- 目的と背景を書く。誰のために、何を解決するために作られたかを含める。
- 現状を「動いているもの」と「止まっているもの」に分けて書く。
- 日常の運用手順(定期実行、監視、障害時の一次対応)を書く。
- 既知の問題と、その回避策を対で書く。回避策がない場合は「なし」と明記する。
- 未完了タスクを優先度付きで書き、着手済みのものは進捗と作業ブランチを添える。
- アクセス権と秘密情報の所在を書く。値は書かず、どこにあるか、誰が発行できるかだけを書く。

### SHOULD

- 関係者を役割つきで書く(依頼元、承認者、運用担当、外部ベンダー)。
- 大きな判断の経緯を書く。採用しなかった案と、その理由を含める。
- 担当交代の 2 週間前までに初版を書き、引き継ぎ相手のレビューを受ける。
- 引き継ぎ相手が資料だけを見て作業を 1 つ再現できるか、実際に試して確認する。
- README と重複する内容は書かず、README へのリンクで済ませる。

### MAY

- 過去の障害と対応の記録を時系列で添えてもよい。
- 引き継ぎ後 1 か月間の質問窓口を書いてもよい。

## Good / Bad 例

```text
# Bad: 状態が分からず、秘密情報の値まで書いている
- バッチは多分動いてる
- DB のパスワードは P@ssw0rd
- 残タスクいろいろ

# Good
## 現状
- 動いているもの: 日次集計バッチ(毎日 06:00、GitHub Actions)
- 止まっているもの: Slack 通知。2026-08-20 から API 変更で失敗。Issue #42

## アクセス権と秘密情報
| 対象 | 所在 | 発行者 |
| --- | --- | --- |
| DB 接続情報 | 1Password「project-x」Vault | インフラ担当 |
| Slack Bot Token | GitHub Secrets `SLACK_TOKEN` | 情シス |

## 未完了タスク
| 優先度 | 内容 | 状態 |
| --- | --- | --- |
| 高 | Slack 通知の修復 | 未着手。Issue #42 |
| 中 | ログのローテーション設定 | ブランチ feature/log-rotate で 50% |
```

```text
# Bad: 結果だけで理由がない
- Redis は使っていない

# Good: 判断の経緯が分かる
- キャッシュに Redis を検討したが、対象データが 1 日 1 回しか更新されないため
  ファイルキャッシュを採用した(2026-05-12、依頼元と合意)
```

## チェックリスト

- [ ] 目的と背景が書かれているか
- [ ] 動いているもの、止まっているものが分かれているか
- [ ] 運用手順を見て一次対応ができるか
- [ ] 既知の問題に回避策が対で書かれているか
- [ ] 未完了タスクに優先度と状態があるか
- [ ] 秘密情報の値が書かれていないか
- [ ] 所在と発行者が分かるか
- [ ] 初見の人が資料だけで作業を 1 つ再開できるか

## 例外

- 運用が既に終了し、アーカイブするだけのリポジトリは「終了済み」と理由を README に書けば HANDOVER.md を省いてよい。
