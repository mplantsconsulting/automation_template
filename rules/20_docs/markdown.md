# Markdown の書き方

| 項目 | 内容 |
| --- | --- |
| 対象 | リポジトリ内のすべての Markdown ファイル(README、ルール、設計メモ、引き継ぎ資料) |
| レベル | 必須 |
| 最終更新 | 2026-09-10 |

## 目的

Markdown は書き方の自由度が高く、書き手ごとに崩れやすい。
崩れた文書は GitHub 上での表示が乱れ、Lint も通らず、検索や差分レビューの邪魔になる。
ここでは表示と差分の両方で読みやすい最小限の書式を定める。

## ルール

### MUST

- 1 ファイルに h1(`#`)は 1 つだけ置き、ファイル冒頭に書く。
- 見出しは `#` から順にレベルを下げ、`##` の次に `####` のように飛ばさない。
- 見出しの前後には空行を 1 行ずつ入れる。
- 箇条書きの記号は `-` に統一する。番号付きリストは順序に意味がある手順にだけ使う。
- 表は 1 行目をヘッダーにし、2 行目に区切り行を置く。
- コードブロックには必ず言語を指定する。該当する言語がなければ `text` と書く。
- リポジトリ内へのリンクは相対パスで書く。絶対 URL は外部サイトにだけ使う。
- 画像には内容を説明する alt テキストを必ず書く。

### SHOULD

- 1 文は短く書き、1 行に 1 文を置く。
- 行末にスペースを残さない。改行は空行で表す。
- 太字は本当に強調したい語にだけ使う。1 段落に 2 か所以上あれば見直す。
- 絵文字は使わない。意味は言葉で伝える。
- 図は画像ファイルより Mermaid を優先する。差分が追え、更新もしやすい。
- 行の長さは目安として 120 文字以内に収める。表と URL は例外とする。

### MAY

- Lint に markdownlint などを使い、CI で上のルールを機械的に確認してもよい。
- 長い文書では冒頭に目次を置いてもよい。

## Good / Bad 例

````text
# Bad: 見出しレベルの飛び、記号の不統一、言語指定なし
# タイトル
### セットアップ
* 手順 1
+ 手順 2
```
npm install
```

# Good
# タイトル

## セットアップ

1. 依存をインストールする。
2. 設定ファイルをコピーする。

```bash
npm install
```
````

````text
# Bad: 絶対 URL、alt なし、太字の乱用
**詳細**は **[こちら](https://github.com/org/repo/blob/main/docs/design.md)** を **参照**。
![](images/flow.png)

# Good
詳細は [設計メモ](docs/design.md) を参照する。
![注文処理のフロー図](images/flow.png)
````

## チェックリスト

- [ ] h1 がファイル冒頭に 1 つだけあるか
- [ ] 見出しレベルが飛んでいないか
- [ ] 見出しの前後に空行があるか
- [ ] 箇条書きが `-` に統一されているか
- [ ] すべてのコードブロックに言語指定があるか
- [ ] リポジトリ内リンクが相対パスか
- [ ] 画像に alt テキストがあるか
- [ ] 行末スペースと絵文字がないか

## 例外

- 外部ツールが自動生成する Markdown(API リファレンスなど)は、生成物であることをファイル冒頭に書けばこのルールの対象外とする。
- GitHub の Issue / PR テンプレートの front matter は、ツールの仕様に従う。
