# README の書き方

| 項目 | 内容 |
| --- | --- |
| 対象 | すべてのリポジトリのルートに置く README.md |
| レベル | 必須 |
| 最終更新 | 2026-09-10 |

## 目的

README はリポジトリを初めて開いた人が最初に読むファイルである。
ここに手順がないと、環境構築のたびに担当者へ質問が飛び、口頭の知識が属人化する。
README だけで「動かして、試して、直せる」状態を保つことがこのルールの目的である。

## ルール

### MUST

- 冒頭に「何をするものか」を 1 段落で書く。誰のどの課題を解決するかを含める。
- 前提環境(OS、ランタイムのバージョン、必要な外部サービス)を書く。
- セットアップ手順、実行方法、テスト方法をそれぞれ独立した節に書く。
- コマンドはそのままコピーして実行できる形で書く。プレースホルダは `<...>` で明示する。
- 設定項目と環境変数を一覧にし、必須かどうかと用途を書く。値そのものは書かない。
- ディレクトリ構成を書き、主要なディレクトリの役割を 1 行で説明する。
- 連絡先または担当者を書く。個人名が変わりやすい場合はチーム名やチャンネル名にする。

### SHOULD

- よく起きる問題と対処をトラブルシュート節に書く。
- 変更履歴は README に書かず CHANGELOG.md に分ける。
- 詳細な設計や仕様は README に書かず `docs/` に置き、README からリンクする。
- セットアップ手順や環境変数を変えた PR では README も同じ PR で更新する。
- 手順は上から順に実行すれば完了する順序で書く。
- 雛形として [../../templates/README_template.md](../../templates/README_template.md) を使う。

### MAY

- 動作イメージを示すスクリーンショットや Mermaid 図を添えてもよい。
- 3 か月に 1 回、README の手順どおりに環境構築できるか確かめてもよい。

## Good / Bad 例

````text
# Bad: 何のためのものか分からず、コマンドも動かない
# my-tool
便利ツールです。
setup してから run してください。

# Good
# my-tool

営業日報の CSV を集計し、週次レポート PDF を生成するツール。
手作業で 2 時間かかっていた集計を 1 コマンドにする。

## 前提環境

- Python 3.12 以上
- Google Cloud のサービスアカウント(Drive 読み取り権限)

## セットアップ

```bash
git clone <repository-url>
cd my-tool
pip install -r requirements.txt
cp .env.example .env
```
````

```text
# Bad: 値を README に書いている
API_KEY=sk-live-1234567890

# Good: 用途と必須かどうかだけを書く
| 変数名 | 必須 | 用途 |
| --- | --- | --- |
| API_KEY | 必須 | 外部 API の認証キー。管理者から受け取る |
```

## チェックリスト

- [ ] 冒頭 1 段落で目的が分かるか
- [ ] 前提環境にバージョンが書かれているか
- [ ] セットアップ、実行、テストの手順がコピペで動くか
- [ ] 環境変数の一覧があり、値が書かれていないか
- [ ] ディレクトリ構成が現状と一致しているか
- [ ] 連絡先または担当があるか
- [ ] 変更履歴や詳細設計が README に混ざっていないか

## 例外

- 使い捨てのスクリプトだけを置くリポジトリは、目的と実行方法の 2 節だけでもよい。
- モノレポ内のサブパッケージは、ルート README からリンクされていれば前提環境の節を省いてよい。
