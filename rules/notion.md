# Notion

案件情報と社内ドキュメントを Notion で管理するときの、置き場所と書き方を定める。

「推奨」「任意」「例外」と明記した項目以外は必須とする。

## 階層

```text
ワークスペース
└─ Operations                      全データベースの入口
   ├─ 🏢 クライアント              取引先。1 社 1 行
   │  └─ 🚀 プロジェクト           案件。1 案件 1 行
   │     ├─ ✅ タスク              作業。1 作業 1 行
   │     ├─ 🗂 リポジトリ          コード。1 リポジトリ 1 行
   │     │  └─ 🐛 Issue/PR         GitHub から自動同期
   │     └─ ⚠️ インシデント        障害と対応。1 件 1 行
   ├─ 👥 メンバー                  担当者。プロジェクトとタスクから参照
   └─ 全社ダッシュボード           KPI の集計ビュー。閲覧専用
```

文書はこの 4 段で考える。

| 段 | 置き場所 | 入れるもの |
| --- | --- | --- |
| 1 | データベースの列 | 集計・絞り込みに使う値 |
| 2 | 行の本文 | その行だけに必要な説明 |
| 3 | 行の子ページ | 設計、議事録、報告など長い資料 |
| 4 | 個人ページ | 共有前の下書き |

### 必須

- 集計や絞り込みに使う情報は列に入れ、本文へ文章で書かない。
- 案件に関する資料はプロジェクト行の子ページに置き、トップレベルへ新しいページを作らない。
- 新しいデータベースを作る前に、既存データベースの列で表せないか確認する。
- Operations 直下のデータベース構成を変える場合は事前に合意を取る。

### 推奨

- 1 つの資料は 1 か所に置き、他の場所からはページメンションで参照する。
- 同じ説明を 2 か所に書かず、正とする側へリンクする。

## ページ

### 必須

- タイトルは内容が分かる体言止めにし、日付や版数を入れない。
- 冒頭 1〜3 行に目的と結論を書く。
- 見出しは H2 から始める。ページタイトルが H1 にあたる。
- 決定事項と未決事項を分けて書き、未決には担当と期限を書く。
- 他ページの参照はページメンションで書き、URL を直接貼らない。
- 画像だけで説明せず、要点を文章でも書く。

### 推奨

- 長いページは冒頭に目次を置く。
- 更新したら冒頭の結論も合わせて直す。
- 図はページ内の図形機能か Mermaid を使い、画像の貼り付けを避ける。

## データベース

### 必須

- 1 行を 1 つの実体に対応させ、同じ実体を複数行に分けない。
- プロパティ名は日本語で統一し、`見積工数h` のように単位を名前へ含める。
- 他のデータベースを参照する列はリレーションにし、名前をテキストで持たない。
- 合計や比率はロールアップか数式で作り、手入力の集計列を作らない。
- ステータスと選択肢はデータベースごとに定めた値だけを使い、勝手に追加しない。
- ビューには用途が分かる名前を付ける。

### 推奨

- 個人用の絞り込みは個人ビューにし、共有ビューを変更しない。
- 使わなくなった列はすぐ消さず、未使用であることを確認してから消す。
- プロジェクトページのタスク表示にはインラインのリンクドビューを使う。

## 各データベースの使い分け

| データベース | 1 行の単位 | 親 | 必ず埋める |
| --- | --- | --- | --- |
| 🏢 クライアント | 取引先 1 社 | なし | 会社名、ステータス、業界 |
| 🚀 プロジェクト | 案件 1 件 | クライアント | プロジェクト名、クライアント、ステータス、開始日、担当 |
| ✅ タスク | 作業 1 件 | プロジェクト | タスク名、プロジェクト、担当者、ステータス、見積工数h |
| 🗂 リポジトリ | GitHub リポジトリ 1 つ | プロジェクト | リポジトリ名、関連プロジェクト |
| 🐛 Issue/PR | Issue または PR 1 件 | リポジトリ | 自動同期のため手入力しない |
| ⚠️ インシデント | 障害 1 件 | プロジェクト | タイトル、発生日、カテゴリ、原因、対応・解決方法 |
| 👥 メンバー | 人 1 名 | なし | 氏名、役職、在籍状況 |

### 必須

- 親が決まっている行は、作成時にリレーションを設定する。
- タスクは親タスクと子タスクの 2 段にする。親を `N. 機能のまとまり`、子を `N-M. 具体的な作業` と名付け、番号で実施順序が分かるようにする。
- 見積工数は子タスクにだけ入れる。親タスクには入れず、子からの集計に任せる。
- 子タスクは 1 件が 1 つの PR に対応する粒度にする。
- タスクは着手前に作り、完了時にステータスと実績工数を入れる。
- インシデントは発生の都度作り、原因と対応を後から追記する。

### 推奨

- プロジェクトのステータスは週次で見直す。
- 見積と実績の差が大きい場合は、理由をタスクの説明に残す。

## 自動更新される列

GitHub からの同期スクリプトが書き込む列がある。

| 列 | 対象 |
| --- | --- |
| `最新PR`、`最新PRリンク`、`最新PR状態`、`最新PR更新日時` | リポジトリ、プロジェクト |
| `最終同期日時` | リポジトリ |
| Issue/PR データベースの全列 | Issue/PR |

### 必須

- これらの列を手で編集しない。次回の同期で上書きされる。
- API で行を作るときは、オートメーションが作成の数秒後に列を上書きすることを前提にする。残す必要がある値は、時間をおいて読み直して確認する。
- 値が誤っている場合は同期スクリプト側を直す。
- 同期対象のデータベースをインテグレーションへ共有したままにする。
- プロジェクトの `リポジトリ` リレーションを空のままにしない。空だと集計が書き込まれない。

## GitHub との対応

### 必須

- PR とタスクを相互に紐付け、どちらからでも辿れるようにする。詳細は [Git と Pull Request](git.md) に従う。
- タスクデータベースに ID プロパティを置き、接頭辞を `TSK` にする。
- リポジトリを新規作成したら、リポジトリデータベースの行とプロジェクトへの紐付けを作る。

## 権限と秘密情報

### 必須

- 鍵、パスワード、接続情報を本文やコメントに書かない。所在と発行者だけを書く。
- 顧客の個人情報を書かない。必要な場合は識別子だけを書く。
- 外部共有リンクを既定で作らない。作る場合は期限を設定し、不要になったら解除する。
- 社外ゲストは必要なページだけに招待する。

### 推奨

- 退職や契約終了の時点で、招待とインテグレーションの権限を見直す。

## 例外

- 共有前の下書きは個人ページに置いてよい。共有する時点で所定の階層へ移す。
- 顧客から受け取った資料は、体裁を整えず原文のまま添付してよい。
- 全社ダッシュボードのように集計だけを目的とするページは、本文の書式ルールを緩めてよい。
