# 表示と操作性

| 項目 | 内容 |
| --- | --- |
| 対象 | ユーザーが見る・操作するすべての画面(Web、デスクトップ、社内ツールを含む) |
| レベル | 必須 |
| 最終更新 | 2026-09-10 |

## 目的

「何が起きたのか分からない」「次に何をすればいいか分からない」画面は、問い合わせと操作ミスを生む。
アクセシビリティを後回しにすると、特定のユーザーが使えないだけでなく、後から直すコストが作るときの何倍にもなる。
ここでは最低限守るべき表示と操作の基準を定める。

## ルール

### MUST

- エラー文言には「何が起きたか」と「ユーザーが次に何をすればいいか」の両方を書く。エラーコードや例外メッセージだけを表示しない。
- 1 秒以上かかる可能性のある処理では、処理中であることを必ず画面に示す(スピナー、進捗、ボタンの無効化など)。
- 削除・上書き・送信などの取り消せない操作は、実行前に確認を入れる。確認文には対象(何を削除するか)を明記する。
- ボタンやリンクの文言は、その操作を表す動詞で書く(例: 「保存する」「削除する」)。「OK」「はい」「送信」だけの文言にしない。
- フォームのバリデーションエラーは、該当する入力欄の直近に表示する。画面上部にまとめて出すだけにしない。
- すべての操作をキーボードだけで完了できるようにする。フォーカスが当たっている要素が目で分かるようにする。
- 意味を持つ画像には代替テキストを付ける。装飾のみの画像は代替テキストを空にし、読み上げ対象から外す。

### SHOULD

- 色だけで意味を伝えない。状態の違いはアイコン、文字、形でも区別できるようにする。
- 文字と背景のコントラスト比は 4.5:1 以上を目安にする。薄いグレーの文字を本文に使わない。
- 画面で使う用語はプロジェクトの用語集に沿って統一する。同じものを「顧客」「お客様」「ユーザー」と呼び分けない。
- 画面幅が狭い環境(スマートフォン、分割表示)でも横スクロールなしで主要な操作ができるようにする。
- 成功時もフィードバックを出す(例: 「保存しました」)。無言で画面が変わるだけにしない。
- 入力欄にはラベルを付け、プレースホルダーをラベルの代わりにしない。

### MAY

- 用語集は `docs/glossary.md` などに置き、画面文言のレビュー時に参照してもよい。
- 主要な画面は、スクリーンリーダーやキーボードのみで一度操作して確認してもよい。

## Good / Bad 例

```text
# Bad: 何が起きたか、次に何をすべきか分からない
"Error: 500"
"処理に失敗しました"

# Good: 原因と次の行動が分かる
"保存に失敗しました。ネットワーク接続を確認して、もう一度「保存する」を押してください。"
"ファイルサイズが上限(10MB)を超えています。ファイルを小さくして再度選択してください。"
```

```text
# Bad: 確認なしで削除、文言も曖昧
[OK] を押すと削除される

# Good: 対象を明記し、操作を動詞で示す
「注文 #1234 を削除します。この操作は取り消せません。」
[キャンセル] [削除する]
```

```text
# Bad: 色だけで状態を区別
● 緑 = 正常   ● 赤 = 異常

# Good: 色 + 文字/アイコンで区別
✔ 正常   ✖ 異常(要対応)
```

## チェックリスト

- [ ] すべてのエラー文言に「何が起きたか」と「次に何をするか」が書かれているか
- [ ] 時間のかかる処理で処理中の表示があるか。二重実行を防いでいるか
- [ ] 取り消せない操作に確認があり、対象が明記されているか
- [ ] ボタンの文言が動詞になっているか
- [ ] バリデーションエラーが入力欄の近くに表示されるか
- [ ] マウスなしで全操作ができるか。フォーカス位置が見えるか
- [ ] 画像に代替テキストがあるか。色以外でも意味が伝わるか
- [ ] 用語が用語集と一致しているか

## 例外

- 自分だけが使う使い捨てスクリプトの CLI 出力は、このルールの対象外とする。
- 社内限定で利用者が特定できるツールでは、レスポンシブ対応(SHOULD)を省いてよい。ただし README に対象環境を書く。
