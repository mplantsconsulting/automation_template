# ソースコード

変更の影響範囲を小さくし、設定・失敗・判断理由を追跡できる構造にする。

「推奨」「任意」「例外」と明記した項目以外は必須とする。

## 構成

- 入口は引数の受け取りと処理の呼び出しだけにする。
- 入出力、業務ロジック、外部連携を分け、依存を外側から内側への一方向にする。
- 循環依存を作らない。
- テストは本番コードの構成に対応させる。
- `util`、`common`、`misc` のような何でも入る場所を作らない。

### 推奨

- 外部サービスへの接続は差し替え可能な境界へ集約する。
- 運用スクリプトは `scripts/` に分ける。
- 1 ファイルが 300 行を超えたら、行数より責務の混在を基準に分割を検討する。

## 関数とクラス

- 1 関数を 1 責務にし、副作用と純粋な計算を分ける。
- 引数は 4 個までにし、関連する値は構造体へまとめる。
- 真偽値のフラグ引数で挙動を切り替えず、目的別の関数か列挙型を使う。
- 戻り値の型を一定にし、グローバルな可変状態を使わない。

### 推奨

- 早期リターンで正常系のネストを浅くし、ネストは 3 段までを目安にする。
- クラスは状態と振る舞いが結びつく場合にだけ使う。
- 省略可能な引数のデフォルト値には不変な値を使う。

## 設定

- 環境依存値をコードへ直書きせず、起動時に 1 か所で読み込んで検証・型変換する。
- 必須設定が欠けている場合は起動時に失敗させ、処理中に環境変数を直接読まない。
- `.env.example` に変数名、用途、ダミー値を書き、実値を含む `.env` をコミットしない。

### 推奨

- デフォルト値はデバッグ無効、外部送信なし、最小権限など安全側にする。
- 設定を変更したら `.env.example` と README を同じ PR で更新する。

## エラーとログ

- 例外は処理できる場所でだけ捕捉し、握りつぶさない。
- 想定内の業務エラーと予期しない障害を区別する。
- エラーメッセージには対象、原因、結果、調査用の識別子を含める。

### 推奨

- ログはログ機構を通して構造化し、相関 ID を含める。
- 同じ失敗を複数層で記録せず、処理した場所で 1 回だけ記録する。
- 再試行は冪等な操作に限り、最大回数と間隔を決める。
- 例外を変換する場合は元の原因とスタックトレースを保持する。

## コメント

- コードから分かる「何をしているか」を書かず、判断や制約の「なぜ」を書く。
- 公開 API の docstring に目的、引数、戻り値、例外を書く。
- コードと同じ PR でコメントを更新し、古いコメントを削除する。
- コメントの言語はプロジェクト内で統一する。

### 推奨

- `TODO` と `FIXME` には担当者か Issue 番号を付ける。
- 外部仕様に基づく実装には出典を添える。

## 例外

- 小規模プロジェクトでは層を減らしてよいが、入口と外部連携は分ける。
- 自動生成コードは生成元を明記し、手で修正しない。
