# Pull Request

| 項目 | 内容 |
| --- | --- |
| 対象 | Pull Request を作成する人、レビューする人 |
| レベル | 必須 |
| 最終更新 | 2026-09-10 |

## 目的

PR はレビューによって不具合を `dev` や `main` に入る前に止める最後の関門である。
本文が「何を作ったか」を伝えていないと、レビュアーは差分を頭から読むことになり、目を通したつもりで承認する。
PR を細かく立てすぎると、逆にレビューされなくなる。
ここでは PR を立てる基準、本文の書き方、出す前のセルフチェック、マージの方式を定める。

## ルール

### PR を立てるかどうか

| 変更 | やり方 |
| --- | --- |
| ドキュメントの修正、設定の一行変更、レビュー指摘の後始末 | `dev` に直接コミットして push |
| 機能追加、設計判断を含む変更 | `dev` から作業ブランチを切り、`dev` に向けて PR |
| リリース | `dev` から `main` に PR |

PR は機能単位に分ける。細かく立てすぎるとレビューされない。
`main` への直接 push は [branch.md](branch.md) のとおり禁止する。

### MUST

- 本文の冒頭の見出しは `## 目的` に固定する。「背景」「概要」「なぜ必要か」などに言い換えない。読む側が毎回同じ位置で同じことを探せるようにする。
- `## 目的` には 1〜3 文で「何がしたいのか」と「なぜ必要なのか」を書く。「◯◯できるようにします」の形で書き、機能の羅列にしない。既にある問題を数字で示せるなら示す。
- マージの前提になる条件(「これを確認してからマージしてほしい」)は `## 目的` の中に書く。独立した節や末尾の注意書きにしない。
- 「特に見てほしいところ」を 1〜3 箇所、理由を添えて名指しする。差分の一覧は GitHub が出すので、本文には「どこを見てほしいか」を書く。
- 本文は丁寧語(です・ます)で書く。人に読んでもらうものなので断定形で書き下さない。コード中のコメントは従来どおり簡潔な形でよい。
- PR を出す前に「出す前のセルフチェック」をすべて実行し、結果を本文か報告に含める。人に指摘される前に自分で見つける。
- タイトルはコミットメッセージと同じ `type: 要約` の形式で書く。
- レビューで受けた指摘にはすべて返答する。修正した、修正しない、後で対応するのいずれかを明示し、修正しない場合は理由を書く。

### SHOULD

- 主要なファイルを `## 対象ファイル` の表で挙げ、それぞれ何が入っているかを 1 行で書く。数が少なければ表は省いてよいが、見どころは必ず書く。
- 次の節は該当するときだけ書く。
  - **設計上の判断**: 迷った箇所と、選ばなかった案。数字で決めたなら根拠の数字を出す。
  - **確認方法と結果**: 実行したコマンドと、通ったこと。CI が同じ結果を表示するプロジェクトでは書かない。
  - **残る制約**: できていないこと。レビュアーが判断に使う情報だけを書き、保険をかけるだけの文章にしない。
- 本文の長さに上限は設けない。ただしレビュアーが読む時間を本文で使い切らせない。
- 作業途中でレビューを受けたい場合や CI の結果を見たいだけの場合は Draft で作成し、レビュー可能になったら Draft を解除する。
- レビュアーは「動作の正しさ」「読みやすさ」「テストの有無」「セキュリティ」「既存ルールとの整合」の観点で見る。好みの違いは指摘の中で「好み」と明示する。
- 指摘は「何が問題か」と「どう直すべきか」を対で書く。修正必須なのか提案なのかを区別できるようにする。

### MAY

- 画面の変更を含む PR はスクリーンショットや動画を添えてもよい。
- 大きな設計変更は、実装 PR の前に設計だけを説明した Issue や Draft PR で合意を取ってもよい。

### 本文に書かないこと

- **レビュー指摘の修正履歴。** 本文は「何を作ったか」の説明であって変更履歴ではない。経緯はコメントに書く。
- **作業の経緯や端末間の往復。** 「実機で見つかったので直した」「当初は不合格だった」「〜する予定だったが不要になった」は変更履歴であって説明ではない。直した後の仕様と、その理由だけを書く。
- コードを読めば分かること。関数の羅列や、差分の言い換え。
- 長い実行ログ。結論だけ書く。
- CI が表示するもの(テストの件数やゲートの通過)。CI がないプロジェクトでは「確認方法と結果」として書く。
- 保険をかけるだけの「未検証です」「〜かもしれません」。レビュアーが判断に使う情報なら「残る制約」に事実として書き、免責のためだけなら書かない。

## 出す前のセルフチェック

まとめて回すターゲット(例: `make review`)を用意しているプロジェクトなら、それを使う。
各項目の詳細は参考に挙げた各ルールに従う。ここでは PR を出す直前に確認する観点だけを列挙する。

### 1. 1 ファイル 1 責務

```bash
git ls-files | xargs wc -l | sort -rn | head -10
```

- 300 行を超えたファイルは分割を提案する。責務が混ざっている兆候は次のとおり。
  - import の並びが無関係な塊に分かれている
  - ファイル名が `utils` `common` `constants` `misc` のように中身を表していない
  - 「変更する理由」が 2 つ以上ある(データの追加と出力仕様の変更が同じファイルにある等)
- 分割しないと判断したなら、その理由を本文に書く。

### 2. テストが足りているか

```bash
git diff --name-only ベースブランチ...
```

- 追加した公開関数・エンドポイント・CLI 引数にテストがあるか。
- 追加した分岐にテストがあるか。特にエラー経路。
- バグを直したなら、そのバグを再現するテストを足したか。足していないなら再発する。
- その再現テストが、修正前のコードで落ちることを確認したか。落ちないテストは何も守っていない。修正を一時的に戻して走らせ、落ちた件数を報告に含める。
- テストが実装の内部構造ではなく振る舞いを見ているか。

### 3. 潜在的なエラーへの対処

「エラーにならず黙って壊れる」経路を先に探す。例外で落ちる失敗より、それらしい結果が出続ける失敗のほうが発見が遅れ、被害が大きい。

- 追加・変更した外部との接点(ファイル、ネットワーク、DB、サブプロセス、別パッケージ)は、失敗したとき何が起きるかを決めてあるか。握り潰していないか。
- 空・0 件・null・重複・境界値の入力で何が起きるかを決めてあるか。「来ないはず」なら、その理由をコメントに書く。
- 失敗を「数えて続ける」のか「即座に止める」のかを選び、明示しているか。数えて続けるなら、最後に失敗を報告して終了コードに反映しているか。
- 途中で失敗したとき、中途半端な状態が残らないか(トランザクションで囲む、別名で書いてから置き換える)。
- 広い例外捕捉に理由があるか。

### 4. セキュリティ

```bash
git diff --cached | grep -inE "api[_-]?key|password|secret|token" | grep -v example
```

- 秘密情報(API キー、認証情報、顧客データ)が差分に入っていないか。
- 外部サービスへ送信するデータが増えていないか。増えたなら本文に明記する。
- 外部から来る入力を検証しているか。
- 例外メッセージやログに秘密情報が漏れていないか。

### 5. 冗長性

未使用コード検出ツール(例: vulture、knip)があれば実行する。

- 同じロジックが 2 箇所以上にないか。あれば 1 箇所に寄せる。
- 呼び出し元がなくなったコードが残っていないか。
- 死んだ設定・使っていない依存が残っていないか。

### 6. 保守性

- 定数やマジックナンバーに名前が付いているか。
- なぜそう書いたかがコードから読み取れないなら、コメントを書く。特に正規表現や閾値。
- 命名が中身と合っているか。`constants` のように「変わらないもの」で括った名前は、性質の違うものを同居させる。
- エラーが「何が起きたか」と「どうすればよいか」を伝えているか。
- 上の裏返しとして、それ以外のコメントは書かない。説明行(コメント + docstring)がファイルの 2 割を超えたら書きすぎを疑う。詳細は [../30_src/comments.md](../30_src/comments.md)。

### 7. ゲート

プロジェクトのチェック(lint / 型 / テスト / ビルド)を通す。出力を `grep` で絞ると失敗を見落とす。落ちたら全文を読む。

```bash
git status --porcelain      # 仮想環境・実データ・ローカル設定が入っていないこと
git check-ignore -v <パス>   # .gitignore のパターンが実際に効いているか
```

`.gitignore` のパターンは実際に効いているかを確かめる。`.venv/` は `.venv-core/` に一致しない。

## マージ

### マージ条件

- CI が通っている。
- 1 名以上の承認がある。
- コンフリクトが解消されている。

### マージ方式

- 作業ブランチから `dev` への単独の PR は `squash` で取り込み、`dev` の履歴を 1 PR = 1 コミットに保つ。
- `dev` から `main` への PR はマージコミット(`--merge`)で取り込む。`squash` すると `main` と `dev` の履歴が分かれ、次回以降のリリース PR に同じ変更が再び差分として現れる。
- 積み上げた PR(別の PR のブランチをベースにした PR)はマージコミット(`--merge`)で取り込む。`squash` と `rebase` はコミットの SHA を書き換えるため、後続 PR の差分に手前の変更が二重に出る。

### 積み上げ PR のマージ順序

1. 手前の PR をマージする。このときベースブランチを削除しない(`--delete-branch` を付けない)。
2. 依存している PR のベースを `dev` に付け替える。
3. その後でベースブランチを削除する。

順序を誤ると PR が復旧不能になる。ベースブランチを削除すると、それを参照している PR は GitHub に自動クローズされ、以降ベースの付け替えも再オープンもできない。

### 履歴を書き換えるとき

`git commit --amend` を複数のブランチで個別に行うと親子関係が切れる。積み上げているブランチを触ったら必ず確認する。

```bash
git merge-base --is-ancestor 手前のブランチ 後続のブランチ && echo 繋がっている
```

切れていたら `git commit-tree` でツリーを保ったまま親を付け直す。

## Good / Bad 例

```text
# Bad: 見出しが揺れ、差分の言い換えと作業経緯だけが書かれている
## 概要
search.py と client.py を追加しました。当初はリトライを入れていましたが不要になったので外しました。
テストは 12 件通っています。未検証の箇所があるかもしれません。

# Good: 目的から始まり、見どころが名指しされている
## 目的

外部サービスから物件を引けるようにします。番号で引けなければ住所に回ります。

## 対象ファイル

| ファイル | 内容 |
| --- | --- |
| `src/foo/search.py` | 検索の流れ。この PR の中心 |
| `src/foo/client.py` | 外部サービスとの通信。新規 |
| `tests/test_search_cli.py` | 終了コードのテスト |

## 特に見てほしいところ

- `search.py` のキーの順序: 実測で決めました。数字の根拠が妥当かを見てください
- `client.py` の例外の切り分け: 認証エラーをリトライしない判断です
```

```text
# Bad: 指摘に無言で対応、または無視
(レビュアー)  この変数名は意味が分かりません
(作成者)      ← 返答なしで push だけする

# Good: 対応と理由を明示
(レビュアー)  この変数名は意味が分かりません
(作成者)      active_user_count に変更しました(a1b2c3d)
(レビュアー)  このヘルパーは共通化できませんか
(作成者)      今回は呼び出し元が 1 か所のため見送ります。2 か所目が出た時点で共通化します
```

## チェックリスト

### 作成者

- [ ] 本文が `## 目的` から始まり、1〜3 文で「何を」「なぜ」が書かれているか
- [ ] 特に見てほしいところが理由付きで 1〜3 箇所書かれているか
- [ ] 本文が丁寧語で書かれ、作業経緯・修正履歴・CI が出す情報が含まれていないか
- [ ] セルフチェック 7 項目を実行し、結果を本文か報告に含めたか
- [ ] タイトルが `type: 要約` の形式か
- [ ] 受けた指摘にすべて返答したか

### レビュアー

- [ ] 見どころとして名指しされた箇所を重点的に読み、判断の根拠が妥当か確認したか
- [ ] 黙って壊れる経路(外部接点の失敗、空・境界値)への対処を確認したか
- [ ] テストが振る舞いを見ており、バグ修正には再現テストがあるか
- [ ] 秘密情報や個人情報の混入がないか
- [ ] 指摘に「問題」と「直し方」の両方を書いたか

## 例外

- 個人開発でレビュアーがいない場合、承認 1 名の条件は免除する。ただしセルフチェックと CI 通過は必須とする。
- 依存ライブラリの一括更新や自動生成コードの再生成など、機械的な変更は 1 ファイル 1 責務のチェックを免除する。本文に「機械的な変更である」と書く。
- 本番障害の緊急修正は Draft を経ずに出してよい。ただし差分は修正に必要な最小限に絞る。
