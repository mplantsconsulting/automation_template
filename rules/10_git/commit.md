# コミット

| 項目 | 内容 |
| --- | --- |
| 対象 | リポジトリにコミットするすべての人 |
| レベル | 必須 |
| 最終更新 | 2026-09-10 |

## 目的

コミット履歴は「なぜこの変更をしたか」を後から辿れる唯一の記録である。
メッセージが `fix` や `update` だけだと、障害調査で履歴を遡っても原因の当たりが付けられない。
また 1 コミットに複数の変更が混ざると、問題のある変更だけを取り消すことができなくなる。

## ルール

### MUST

- コミットメッセージの 1 行目は `type: 要約` の形式で書く。
- `type` は次の中から選ぶ。`feat`(機能追加)、`fix`(不具合修正)、`docs`(ドキュメント)、`refactor`(動作を変えない整理)、`test`(テスト)、`chore`(ビルド・設定・依存など)。
- 1 行目は 50 文字程度に収め、末尾に句点を付けない。
- 1 コミットには 1 つの変更だけを含める。機能追加とリファクタリングを同じコミットにしない。
- コミット前に差分を確認し、不要なファイル(ビルド成果物、個人設定、デバッグ出力、秘密情報)が混ざっていないことを確かめる。
- ビルドやテストが通らない状態のコミットを `dev` や `main` に残さない。

### SHOULD

- 本文には「何を変えたか」ではなく「なぜ変えたか」を書く。差分を見れば分かることは書かない。
- 1 行目と本文の間は 1 行空ける。本文は 1 行 72 文字程度で折り返す。
- 関連する Issue や PR があれば本文に番号を書く(例: `Refs #123`、`Closes #123`)。
- 要約は命令形または現在形で書き、言語はプロジェクト内で統一する。
- WIP(作業途中)コミットは作業ブランチ内だけで使い、PR を出す前に `squash` や `rebase -i` で意味のある単位に整理する。

### MAY

- 破壊的変更や設定変更など、レビュアーに特に注意してほしい点は本文の末尾に `BREAKING CHANGE:` などの見出しを付けて書いてもよい。

## Good / Bad 例

```text
# Bad: 何をなぜ変えたか分からない
fix
update files
WIP

# Good: 種類と要約が 1 行目で分かる
fix: CSV 出力の文字コードを UTF-8 BOM 付きに変更
feat: ログイン画面にパスワード再設定リンクを追加
refactor: 日付整形処理を format_date に集約
```

```text
# Bad: 本文が差分の説明になっている
fix: CSV 出力の文字コードを変更

encoding を utf-8 から utf-8-sig に変えた。

# Good: 本文に理由を書く
fix: CSV 出力の文字コードを UTF-8 BOM 付きに変更

Excel で開くと日本語が文字化けするという報告があった。
Excel は BOM がないと Shift_JIS として解釈するため、BOM を付けて回避する。

Closes #123
```

```text
# Bad: 1 コミットに複数の変更が混在
feat: ログイン画面を追加、あわせて lint 設定も修正

# Good: 変更ごとにコミットを分ける
feat: ログイン画面を追加
chore: lint 設定に未使用 import の検出を追加
```

## チェックリスト

- [ ] 1 行目が `type: 要約` の形式で 50 文字程度に収まっているか
- [ ] `type` が定められた一覧の中から選ばれているか
- [ ] 1 コミットに 1 つの変更だけが含まれているか
- [ ] 本文に「なぜ」が書かれているか
- [ ] 差分に不要なファイルや秘密情報が混ざっていないか
- [ ] WIP コミットが PR に残っていないか

## 例外

- 自動生成されるコミット(依存更新ボット、リリースタグ付けなど)はツールの形式に従ってよい。ただし `type` は可能な限り付ける。
- 緊急のホットフィックスで本文を書く時間がない場合は 1 行目だけでコミットしてよい。ただし PR の説明に理由を必ず書く。
