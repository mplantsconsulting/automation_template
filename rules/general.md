# 全体ルール

すべてのコード、ドキュメント、設定ファイルに適用する。

「推奨」「任意」「例外」と明記した項目以外は必須とする。

## 必須

### 基本原則

- 読みやすさを最優先し、短くても意図が伝わらない書き方をしない。
- 文章は結論を先にし、重複や不要な経緯を省く。
- 1 つの関数、ファイル、PR は 1 つの目的だけを持つ。
- 動かないコード、未使用コード、コメントアウトしたコードを残さない。
- 同じ処理が 3 か所目に必要になった時点で共通化する。
- 外部入力は境界で検証し、異常なら早く失敗させる。
- 変更後は動作を確認し、確認できない変更をマージしない。

### 命名

- 同じ概念には同じ名前を使い、独自の省略語や否定形を避ける。
- 関数は動詞で始め、真偽値は `is`、`has`、`can` などで始める。
- マジックナンバーには意味の分かる定数名を付ける。

### セキュリティ

- 秘密情報や個人情報をコード、設定、ログ、例外メッセージへ出さない。
- 秘密情報は環境変数か秘密管理サービスから取得し、対象ファイルを `.gitignore` に登録する。
- 本番の秘密情報を開発環境やテストで使わない。
- 秘密情報を誤って公開した場合は、履歴の削除だけでなく無効化と再発行を行う。

## 推奨

- 賢い書き方より平凡な書き方を選び、非自明な判断には理由を残す。
- 将来使うかもしれない機能や不要な依存を追加しない。
- 新しいツールや同等機能を作る前に社内の既存ツールを確認し、要件を満たすものを再利用する。
- 単位や型を誤解しやすい値は、`timeout_seconds` や `user_ids` のように名前で示す。
- 言語の命名慣習に従い、プロジェクト内で表記を統一する。
- 外部へ渡す SQL やコマンドは、文字列結合せずパラメータ化された API を使う。
- 依存ライブラリの脆弱性を定期的に確認し、権限と有効期限を最小にする。
- コミット前に秘密情報の混入を検出する仕組みを導入する。
- 既存のコード規約に合わせ、好みだけでスタイルを変えない。

推奨から外す場合は理由を PR に書く。

## 例外

- 数式内など慣習が明確な短いスコープでは、`x` や `i` などの短い名前を使ってよい。
- 外部 API の名前は境界でそのまま扱い、内部へ渡す場合だけプロジェクトの名前へ変換してよい。
- 使い捨ての検証コードでは推奨事項を緩めてよいが、本番コードへ取り込まない。
