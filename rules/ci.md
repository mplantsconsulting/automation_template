# Lint、Formatter、CI

人による確認を動作や設計の議論に使えるよう、機械的な検証を自動化する。

「推奨」「任意」「例外」と明記した項目以外は必須とする。

## Lint と Formatter

- プロジェクトごとに Linter と Formatter を決め、設定をリポジトリで共有する。
- Formatter の出力を正とし、書式の好みをレビューで指摘しない。
- Lint の無視にはコード上で理由を書き、ルールの緩和は設定変更の PR で合意する。

### 推奨

- 実行コマンドをまとめて README に書き、可能ならコミット前にも自動実行する。
- ツールのバージョンを固定し、ローカルと CI で同じコマンドを使う。

## CI

- すべての PR で Lint、テスト、必要なビルドを実行し、成功をマージ条件にする。
- `dev` または `main` の失敗は他の作業より優先して直すか、原因を revert する。
- 秘密情報は CI の Secrets で管理し、設定やログへ出さない。
- 依存はロックファイルどおりにインストールする。
- CI の設定変更も PR でレビューする。

### 推奨

- CI は 10 分以内を目安にし、超える場合は並列化、分割、キャッシュを検討する。
- 依存のインストール結果をキャッシュし、キャッシュキーにロックファイルのハッシュを使う。
- デプロイ方法と承認の有無を README に書く。
- 不安定なテストを再実行だけで通さず、修正まで除外する場合は Issue を作る。

## 任意

- 型検査を CI の必須項目に含めてよい。
- PR ごとのプレビュー環境や、定期的な脆弱性検査・長時間テストを設けてもよい。

## 例外

- 立ち上げ直後でテストがない場合は Lint とビルドだけで始め、最初のテスト追加時にテストジョブを加える。
- 文書だけの変更ではテストとビルドを省いてよいが、Markdown の Lint は実行する。
- 自動生成ファイルは生成元を明記して Lint と Formatter の対象外にしてよい。
