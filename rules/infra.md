# インフラ

クラウドの構成をコードで書くときに、取り違え、データの消失、権限の広げすぎを、レビューとテストで止められる形にする。

組織の統制（レベル、命名、アドレス設計、権限の付与）は aws_setup、AWS の案件の雛形は aws_template を正とし、ここには書き写さない。

「推奨」「任意」「例外」と明記した項目以外は必須とする。

## 構成管理

### 必須

- クラウドのリソースはコードで定義し、コンソールで作成・変更しない。
- デプロイ先の環境とアカウントに既定値を持たせず、無い・食い違う場合は合成（`cdk synth`、`terraform plan`）の段階で止める。
- アカウント ID などデプロイ先の識別子をリポジトリと手元のファイルに置かず、認証情報とデプロイ先のアカウントが持つ値で確かめる。
- ツールがキャッシュする参照の結果（例: `cdk.context.json`）をコミットしない。
- 名前とタグは組織の命名規則に従う。

### 推奨

- 変更の頻度と管理する人が同じリソースを 1 つのスタックにまとめ、独立して止めたいもの（顧客ごとの一式など）は分ける。
- スタック間の受け渡しは名前の規約かパラメータストアで行い、強い参照（CloudFormation の Export など）を避ける。その場合はデプロイの順番を README に書く。

## データを持つリソース

### 必須

- ストレージ、暗号鍵、データベース、秘密情報は、スタックの削除で消えない設定にする（例: `RemovalPolicy.RETAIN`）。
- 公開アクセスを塞ぎ、保存時の暗号化と通信の暗号化の強制を有効にする。
- 秘密情報は入れ物だけをコードで作り、値はデプロイ後に手で入れる。値をコード、テンプレート、デプロイの引数に置かない。
- 手で値を入れた入れ物の初期値を後から変えない。デプロイが手で入れた値を上書きする。

### 推奨

- 暗号化の方式など、後から変えると作り直しになる設定は最初の PR で決め、理由を設計書に書く。

## 権限とネットワーク

### 必須

- 実行ロールには、そのワークロードが触るリソースだけを名指しで許可する。リソースに `*` を使う場合はコードに理由を書く。
- 外から届く経路を作らない。受信を許すルールを足す場合は理由を書く。
- 権限、公開範囲、鍵のポリシーを変える PR は、セキュリティの観点でレビューする（例: `/security-review`）。

### 推奨

- 計算資源はパブリック IP を持たないサブネットに置く。
- 顧客ごとの分離は権限（ロールと鍵）で作り、コードの分岐に頼らない。

## テスト

### 必須

- 合成したテンプレートに対して、壊れたら困る条件をアサーションで確かめる。対象は公開範囲、暗号化、削除保護、権限の範囲、タイムアウトなど。
- スナップショットテストを主にしない。差分が大きく、レビューで読まれない。
- テストは認証情報なしで通るようにし、外部から読む値はテストから渡す。

### 推奨

- 組織の検査（Security Hub など）で FAIL になる設定は、テストで止める。

## デプロイ

### 必須

- 本番の前に、非本番の環境で同じコードをデプロイして確かめる。
- デプロイの前に差分（`cdk diff`、`terraform plan`）を読み、置き換えや削除が出たら理由が分かるまで進めない。
- 本番へのデプロイの方法、必要な権限、順番を README に書く。

### 推奨

- 定期実行などの起動の仕組みは無効の状態でデプロイし、監視が揃ってから有効にする。
- 常時課金されるリソース（NAT、ロードバランサ、DB のインスタンスなど）を足す PR には、月額の目安を書く。
- 非本番の常時課金のリソースは、使うときだけ作れるようにする。

## 例外

- 検証用の使い捨ての環境では、コンソールでの作成を許す。検証が終わったら消す。
