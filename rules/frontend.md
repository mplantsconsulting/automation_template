# フロントエンド

特定のデザインを強制せず、画面の責務、状態、操作性に共通の基準を設ける。

「推奨」「任意」「例外」と明記した項目以外は必須とする。

## 技術選定

### 必須

- 既存アプリは現在の構成を尊重し、統一だけを目的に移行しない。
- 言語やフレームワークを変更する場合は、効果、コスト、移行方法を記録する。

### 推奨

- 新しいブラウザ向け SPA は TypeScript を第一候補にする。
- 別の言語が要件、既存連携、保守体制に適する場合は、理由を README か設計メモに書く。

### 任意

- Python 中心の単純な社内画面では Streamlit、TypeScript の SPA では Vite と Vitest を選んでもよい。

## 部品

### 必須

- 1 部品を 1 責務にし、表示、データ取得、保存、業務ロジックを分ける。
- 表示部品はデータを引数で受け取り、子から親を直接変更しない。
- ページの入口は薄くし、部品名は画面上の役割で付ける。

### 推奨

- 部品は 150 行、引数は 5 個を目安にし、超えたら責務を見直す。
- 共通部品は同じ見た目と振る舞いが 2 回目に必要になった時点で作る。
- スタイルの置き場所をプロジェクト内で統一する。

## 状態と外部接点

### 必須

- 状態は使う最小の範囲に置き、同じ値を複数箇所で持たない。
- 他の状態から計算できる値を保存しない。
- サーバーデータとローカル UI 状態を分け、状態を直接書き換えない。
- API 呼び出しや保存はサービス層など 1 か所へ集約する。
- 外部から受け取った値は境界で検証し、検証前の値を画面や業務ロジックへ渡さない。
- 読み込み中、エラー、空の状態を扱う。

### 推奨

- 失敗時の再試行、エラー表示、ログの扱いを共通化する。

## 表示と操作

### 必須

- エラーには発生内容と次の行動を書き、処理中であることを画面で伝える。
- 取り消せない操作は対象を明示して確認し、二重実行を防ぐ。
- 操作名は動詞で書き、入力エラーを対象項目の近くに表示する。
- キーボードだけで操作でき、フォーカス位置が見えるようにする。
- 画像に代替テキストを付け、色だけで意味を伝えない。

### 推奨

- 本文のコントラスト比は 4.5:1 以上を目安にする。
- ラベルをプレースホルダーで代用しない。
- 狭い画面でも主要操作ができるようにするか、対象環境を README に書く。
- 成功した操作は画面で伝える。

## デザインと確認

### 推奨

- 見た目の方針は各プロジェクトで決め、情報の階層や操作対象の境界を曖昧にしない。
- 色、余白、文字サイズなどの共通値は変数やテーマへ集約する。
- 用語はプロジェクト内で統一する。
- 画面テストは内部構造ではなく、利用者の操作と表示結果を検証する。
- 変更した画面を実際に開き、影響する状態と対象画面幅で確認する。

## 例外

- 使い捨ての検証画面では行数や CI の推奨を緩めてよいが、本番コードへ取り込まない。
- 顧客や外部プラットフォームから技術や表示を指定されている場合は、その指定を優先する。
