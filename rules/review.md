# レビュー

PR を漏れなくレビューするために、当てる観点の選び方、指摘の書き方、見た範囲の示し方を定める。

「推奨」「任意」「例外」と明記した項目以外は必須とする。

## 観点の選び方

### 必須

- [Git と Pull Request](git.md) と [全体ルール](general.md) は、すべての PR に当てる。PR の本文、コミット、差分の大きさ、タスクとの紐付けを、git.md に照らして見る。
- 変えたファイルごとに、[ルール一覧](README.md) で「読む場面」に当たるルールを選び、当てる。
- automation_template のルール集そのものを変える PR には、automation_template の CLAUDE.md の「このリポジトリ自体を直すとき」も当てる。
- 権限、公開範囲、鍵のポリシーを変える PR は、[インフラ](infra.md) に従ってセキュリティの観点でもレビューする。
- AWS の構成を変える PR は、aws/AGENTS.md を読み、`aws/` のルールも当てる。案件のリポジトリに `aws/` が無ければ、automation_template の `aws/` を読む。
- 次の横断の観点は、変えたファイルの種類にかかわらず必ず見る。

| 観点 | 見ること |
| --- | --- |
| 正しさ | 書いたとおりに動くか。手順やルールなら、そのとおりに進めて矛盾や行き止まりがないか |
| エラーと境界 | 失敗、空、0 件、上限、想定外の入力の扱い |
| セキュリティ | 秘密情報、個人情報、権限、公開範囲 |
| テスト | 変えた振る舞いを確かめるテストがあるか。無いなら PR に理由があるか |
| 重複とずれ | 同じことを 2 か所に書いていないか。片方だけ直して、ほかの場所と食い違っていないか |
| 消えたもの | 削除や移動で、決まり、機能、リンクが失われていないか |
| 読みやすさ | コードなら、名前、構造、ネストの深さ、コメントが意図を伝えているか。文書なら、読む人（利用者、AI、レビュアー）がその文書だけで迷わず進めるか |

## 指摘の書き方

### 必須

- 指摘ごとに、重さ、問題、起きること、修正案、根拠のルールを書く。
- 重さは次の 3 つから選ぶ。

| 重さ | 意味 |
| --- | --- |
| 必須 | 直さないとマージしない。この PR が持ち込んだ、または悪くした問題 |
| 提案 | 直したほうがよいが、マージは止めない |
| もともと | この PR より前からある問題。この PR で直すかは作った人が決める |

- 推測だけの指摘は出さない。確かめられなかったものは「未確認」と書いて区別する。
- 書式の好みを指摘しない。Formatter の出力を正とする（[Lint、Formatter、CI](ci.md)）。

### 推奨

- 指摘は重い順に並べる。
- 問題を指摘するときは、どの場面で何が起きるかを 1 つ具体的に書く。

## 見た範囲

### 必須

- レビューの最後に、当てたルールと横断の観点ごとに、「指摘あり」「問題なし」「該当なし」を表で示す。指摘が無かった観点も書き、見ていない観点を残さない。

## 例外

- 誤字の修正だけの PR は、横断の観点のうち「正しさ」と「消えたもの」だけを見ればよい。
