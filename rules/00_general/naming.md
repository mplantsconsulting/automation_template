# 命名

| 項目 | 内容 |
| --- | --- |
| 対象 | 変数、関数、クラス、定数、ファイル、ディレクトリなど名前を付けるものすべて |
| レベル | 必須 |
| 最終更新 | 2026-09-10 |

## 目的

名前はコードの中で最も多く読まれるコメントである。
名前が曖昧だと読み手は実装を読んで意味を推測することになり、推測が外れればバグになる。
ここでは「名前だけで役割と型が分かる」状態を保つための考え方を定める。

## ルール

### MUST

- 同じ概念には同じ名前を使う。`user` と `member` と `account` のように言い換えない。
- 独自の省略語を作らない。`usr`、`cnt`、`tmp2` のような名前は禁止する。`id`、`url`、`html` など広く通じるものだけ許可する。
- 真偽値は `is`、`has`、`can` のいずれかで始める。
- 関数は動詞で始め、何をするかを表す。データを返すだけなら `get`、状態を変えるなら `update`、`save` など動作が分かる動詞を選ぶ。
- 定数は大文字とアンダースコアで書く。マジックナンバーは名前を付けた定数にする。
- 名前に否定を含めない。`is_not_ready`、`disable_flag` のような名前は肯定形で書き直す。

### SHOULD

- 単位や型が誤解されやすいものは名前に含める。`timeout_seconds`、`price_jpy`、`user_ids` のように書く。
- スコープが広いほど長く具体的な名前にする。ループ変数やラムダの引数など数行で消える名前は短くてよい。
- コレクションは複数形にする。`user` は 1 件、`users` は複数件と読めるようにする。
- ファイル名はその中身の主役の名前に合わせる。`utils`、`misc`、`common` のような何でも入る名前は避ける。
- 大文字小文字やアンダースコアの使い分けは言語の慣習に従い、1 つのプロジェクト内で混在させない。

### MAY

- ドメイン固有の用語は用語集を作り、名前とドメイン用語の対応を 1 か所にまとめてもよい。

## Good / Bad 例

```text
# Bad: 省略語と否定形で読み手が止まる
usr_cnt = len(lst)
if not is_not_active:
    ...

# Good: 名前だけで意味が分かる
active_user_count = len(active_users)
if is_active:
    ...
```

```text
# Bad: 単位が分からず、呼び出し側で桁を間違える
def wait(timeout):
    ...
wait(3000)

# Good: 単位を名前に含める
def wait(timeout_seconds):
    ...
wait(3)
```

```text
# Bad: 動詞がなく、値を返すのか副作用があるのか分からない
def user_data(id): ...

# Good: 何をするかが動詞で分かる
def fetch_user(user_id): ...
def save_user(user): ...
```

## チェックリスト

- [ ] 同じ概念に別の名前を使っていないか
- [ ] 一般的でない省略語を使っていないか
- [ ] 真偽値が `is` / `has` / `can` で始まっているか
- [ ] 関数名が動詞で始まり、何をするか分かるか
- [ ] マジックナンバーに名前が付いているか
- [ ] 単位や型を誤解しそうな名前に単位が含まれているか
- [ ] 否定形の名前が残っていないか

## 例外

- 数学的な慣習がある場合(`x`、`y`、`i`、`n` など)は短い名前を使ってよい。ただし数行で完結するスコープに限る。
- 外部 API やライブラリが定めた名前をそのまま受け渡す箇所は、相手側の名前に合わせてよい。境界で変換する場合はその関数の中だけに留める。
