# 全体原則

| 項目 | 内容 |
| --- | --- |
| 対象 | すべてのコード、ドキュメント、設定ファイル |
| レベル | 必須 |
| 最終更新 | 2026-09-10 |

## 目的

コードは書く時間より読まれる時間のほうが長い。
読み手が迷わないコードにしておかないと、修正のたびに調査コストが増え、変更を恐れて放置されるようになる。
ここでは他のすべてのルールの土台となる考え方を定める。

## ルール

### MUST

- 読みやすさを最優先する。短く書けても意図が伝わらない書き方はしない。
- 1 つの関数、1 つのファイル、1 つの PR は 1 つの目的だけを持つ。
- 動かないコード、使われていないコードは残さない。コメントアウトして残すことも禁止する。
- 同じ処理を 2 か所以上に書かない。3 回目に書くときは共通化する。
- 入力の異常は早い段階で検出して失敗させる。黙って続行しない。
- 変更したら必ず動作を確認する。確認できない変更はマージしない。

### SHOULD

- 賢い書き方より平凡な書き方を選ぶ。トリックが必要な場合はコメントで理由を書く。
- 将来使うかもしれない機能は作らない。今必要なものだけを作る。
- 依存ライブラリは本当に必要なものだけ追加する。標準機能で済むなら追加しない。
- 既存のコードの書き方に合わせる。自分の好みでスタイルを変えない。
- 判断に迷ったら、後から変更しやすい方を選ぶ。

### MAY

- 判断の根拠が非自明な設計は、短い設計メモを残してもよい。

## Good / Bad 例

```text
# Bad: 何をしているか読み手が追わないと分からない
result = [x for x in items if x[2] > 0 and x[5] != "N"]

# Good: 名前で意図を伝える
active_paid_items = [
    item for item in items
    if item.amount > 0 and item.status != CANCELLED
]
```

```text
# Bad: 将来のために引数を先回りで用意している
def send_mail(to, subject, body, cc=None, bcc=None, priority=None, retry=None):
    ...

# Good: 今必要なものだけ
def send_mail(to, subject, body):
    ...
```

## チェックリスト

- [ ] 関数名・変数名だけで処理の意図が分かるか
- [ ] 使われていないコードやコメントアウトが残っていないか
- [ ] 同じ処理を別の場所にも書いていないか
- [ ] 異常な入力に対して早く失敗するようになっているか
- [ ] 今回の目的に不要な変更が混ざっていないか

## 例外

- 使い捨てのスクリプト(1 回実行して破棄するもの)は SHOULD を緩めてよい。ただし `scripts/` などに置き、使い捨てであることをファイル冒頭に書く。
