# セキュリティ

| 項目 | 内容 |
| --- | --- |
| 対象 | すべてのコード、設定ファイル、ログ、リポジトリ |
| レベル | 必須 |
| 最終更新 | 2026-09-10 |

## 目的

秘密情報の漏えいは、一度起きると取り消せない。
リポジトリに書いたトークンは履歴を消しても既に複製されている可能性があり、ログに出た個人情報は監査対象になる。
ここでは「漏らさない」ことと「漏れたときにすぐ止められる」ことの両方を守るためのルールを定める。

## ルール

### MUST

- API キー、パスワード、トークン、秘密鍵などの秘密情報をコードや設定ファイルに直接書かない。環境変数か秘密管理サービスから読み込む。
- 秘密情報を含むファイル(`.env`、鍵ファイル、認証情報の JSON など)は `.gitignore` に登録し、リポジトリに含めない。
- ログや例外メッセージにトークン、パスワード、個人情報を出力しない。出力が必要な場合は先頭数文字以外をマスキングする。
- 外部から受け取る入力(リクエスト、ファイル、環境変数、CLI 引数)は使う前に型と範囲を検証する。検証に失敗したら即座に処理を止める。
- 秘密情報を誤ってコミットしたら、履歴の削除だけで終わらせず、その秘密情報を必ず無効化して再発行する。
- 本番環境の秘密情報を開発環境やテストコードで使わない。

### SHOULD

- 依存ライブラリの既知の脆弱性を CI で定期的に確認し、重大なものは検出後すぐ更新する。
- コミット前に秘密情報の混入を検出する仕組み(例: `git-secrets`、`gitleaks`、`pre-commit` のフック)を入れる。
- 秘密情報の発行時に有効期限と権限の範囲を最小にする。読み取りだけで済むなら書き込み権限を付けない。
- 設定ファイルには `.env.example` のように「キー名だけを書いた見本」を用意し、値は書かない。
- SQL やシェルコマンドなど外部に渡す文字列は、文字列結合ではなくパラメータ化やエスケープ済みの API を使って組み立てる。

### MAY

- 秘密情報の所在(どのサービスで管理し、誰が発行できるか)を README や引き継ぎ資料に書いてもよい。値そのものは書かない。

## Good / Bad 例

```text
# Bad: 秘密情報がコードに埋め込まれている
API_KEY = "sk-live-1234567890abcdef"
client = Client(api_key=API_KEY)

# Good: 環境変数から読み、無ければ即失敗する
API_KEY = env.require("API_KEY")
client = Client(api_key=API_KEY)
```

```text
# Bad: ログにトークンがそのまま出る
log.info("request headers: " + headers)

# Good: 秘密情報はマスキングして出す
log.info("request headers: " + mask_secrets(headers))
# => Authorization: Bearer sk-l****
```

```text
# Bad: 誤コミット後に履歴を消しただけ
git filter-repo --path .env --invert-paths

# Good: 履歴の削除に加えて、必ず無効化と再発行を行う
1. 該当トークンを発行元で無効化する
2. 新しいトークンを発行し、秘密管理サービスに登録する
3. 履歴から削除し、関係者に周知する
```

## チェックリスト

- [ ] 秘密情報がコードや設定ファイルに直接書かれていないか
- [ ] `.env` や鍵ファイルが `.gitignore` に含まれているか
- [ ] ログや例外メッセージに秘密情報や個人情報が出ないか
- [ ] 外部からの入力を検証してから使っているか
- [ ] 追加した依存ライブラリに既知の脆弱性がないか
- [ ] 秘密情報の権限と有効期限が最小になっているか

## 例外

- ローカル開発専用でダミーの値であることが明白なもの(例: `password` というテスト用 DB パスワード)は設定ファイルに書いてよい。ただしファイル名やコメントで「開発専用」と明示し、本番と同じ値を使わない。
- ログの詳細出力がデバッグに不可欠な場合は、開発環境限定のログレベルでのみ出力し、本番では出ないことをコードで保証する。
