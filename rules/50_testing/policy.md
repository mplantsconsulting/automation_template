# テスト方針

| 項目 | 内容 |
| --- | --- |
| 対象 | すべてのソースコードと、それに対するテストコード |
| レベル | 必須 |
| 最終更新 | 2026-09-10 |

## 目的

テストがないコードは、変更したときに何が壊れたか誰にも分からない。
壊れたことに気づけないと修正を恐れて放置され、放置されたコードはさらに直しにくくなる。
ここでは「何をテストし、何をテストしないか」と「テストをどう運用するか」の基準を定める。

## ルール

### MUST

- 新しく追加した機能には、同じ PR でテストを付ける。テストのない機能追加はマージしない。
- バグを修正するときは、まずそのバグを再現する失敗するテストを書き、次に修正してテストを通す。
- ビジネスロジック(計算、判定、状態遷移)は必ずテストする。
- 境界値(0、空、上限、下限、境界の前後 1)とエラー経路(異常入力、失敗時の挙動)をテストに含める。
- すべてのテストを CI で実行し、1 つでも失敗したらマージしない。
- 不安定なテスト(実行するたびに結果が変わる flaky なテスト)は放置しない。原因を直すか、直せないなら削除する。スキップしたまま残さない。

### SHOULD

- 単体テストを厚くし、結合テストは主要な経路だけ、E2E テストは最小限にする。上の層ほど遅く壊れやすいため、下の層で担保する。
- カバレッジは目標にしない。指標として見て、低い箇所を「テストが足りない候補」として確認する。
- 外部ライブラリの内部動作、言語の標準機能、値を返すだけの getter はテストしない。自分たちが書いたロジックをテストする。
- テストが書きにくいと感じたら、テストではなく設計を疑う。依存が多すぎる、責務が混ざっている、副作用が隠れているのが原因であることが多い。
- 1 つのテストの実行は速く保つ。単体テストの全体は数分以内に終わるようにする。

### MAY

- 仕様が固まっていない探索的なコードは、テストを後回しにしてもよい。ただし仕様が固まった時点でテストを追加する。
- 重要な計算ロジックには、性質を検証するテスト(入力を変えても成り立つ条件を確認するもの)を追加してもよい。

## Good / Bad 例

```text
# Bad: バグ報告を受けて、修正だけをコミットした
fix: 月末日の計算がずれる問題を修正

# Good: 再現テストを先に書き、失敗を確認してから修正した
test: 2 月末日で翌月計算がずれることを再現するテストを追加  (失敗する)
fix: 月末日の計算がずれる問題を修正                       (テストが通る)
```

```text
# Bad: getter と外部ライブラリの内部をテストしている
test_user_name_returns_name:
    user = User(name="a")
    assert user.name == "a"

test_json_library_parses_object:
    assert json.parse('{"a": 1}') == {"a": 1}

# Good: 自分たちが書いた判定ロジックの境界とエラー経路をテストしている
test_discount_is_zero_when_amount_is_below_threshold
test_discount_applies_when_amount_equals_threshold
test_discount_raises_when_amount_is_negative
```

```text
# Bad: 不安定なテストをスキップして放置
@skip("たまに落ちる")
test_order_is_processed_within_timeout: ...

# Good: 原因(時刻依存)を取り除いて安定させる。直せないなら削除する
test_order_is_processed_within_timeout:
    clock = FixedClock("2026-09-10T00:00:00")
    ...
```

## チェックリスト

- [ ] 新機能に対応するテストが同じ PR に含まれているか
- [ ] バグ修正 PR に、修正前は失敗していた再現テストが含まれているか
- [ ] 境界値とエラー経路がテストされているか
- [ ] 外部ライブラリの内部や単純な getter をテストしていないか
- [ ] CI ですべてのテストが実行され、通っているか
- [ ] スキップされたまま放置されているテストがないか

## 例外

- 使い捨てのスクリプト(1 回実行して破棄するもの)はテストを省いてよい。ただし使い捨てであることをファイル冒頭に書く。
- 画面の見た目だけを変更する PR は、既存テストが通ることの確認だけでよい。
- 緊急の障害対応で再現テストを先に書く時間がない場合は、修正を先に入れてよい。ただし同じ日のうちに再現テストを追加する PR を出す。
