プロジェクト `$1` をタスクへ分解し、Notion に登録する。

親タスクを先に作り、その後で子タスクを作る。順序を逆にしない。
ルールは [rules/notion.md](../../rules/notion.md) と [rules/git.md](../../rules/git.md) に従う。

## 命名

| 段 | 形式 | 例 | 見積工数 |
| --- | --- | --- | --- |
| 親 | `N. 機能のまとまり` | `2. AI読込・情報抽出機能開発` | 入れない |
| 子 | `N-M. 具体的な作業` | `2-1. 処理済み案件の再処理防止` | 必ず入れる |

子の番号は親の番号に揃える。番号だけで実施順序が分かるようにする。

## 手順

### 1. 現状を読む

1. `node scripts/notion.mjs project-get $1` でプロジェクトと既存タスクを取得する。
2. `$2` があればその資料を読む。なければプロジェクトページ本文とリポジトリの README を読む。

### 2. 親タスクを作る

3. 資料から機能のまとまりを洗い出し、**親タスクをいくつ作るかを利用者に聞く。** 聞かずに決めない。
   候補と、それぞれに何が入るかを 1 行で添えて示す。
4. 聞いた数に合わせてまとまりを統合または分割し、実施順に `1.` から番号を振る。
5. 親タスクを作る。**見積工数は入れない。** 子の合計がロールアップされる。

   ```bash
   node scripts/notion.mjs task-create --project $1 --name "1. データ取得・投入基盤構築" --kind 開発 --priority 高
   ```

6. 作られた `TSK-000` を親ごとに控える。

### 3. 子タスクを作る

7. 親ごとに作業を分ける。次を守る。

   - **1 子タスクが 1 PR に対応する粒度にする。** PR が 300 行を超えそうなら分ける。
   - 見積工数は 3 時間から 16 時間に収める。超えるものは分割する。
   - 調査だけの子タスクは、成果物(判断、資料、方針)を名前に含める。
   - 既存タスクと重複するものは作らない。

8. 各子タスクに次を決める。

   | 項目 | 引数 | 既定 |
   | --- | --- | --- |
   | タスク名 | `--name` | `N-M. ` で始める。動詞で終える |
   | 親タスク | `--parent` | 必須。手順 6 で控えた `TSK-000` |
   | 見積工数 | `--estimate` | 時間。必須 |
   | 工数区分 | `--kind` | 開発 / PM |
   | 優先度 | `--priority` | 高 / 中 / 低 |
   | 担当者 | `--assignee` | 未定なら省く |
   | 期日 | `--due` | プロジェクトの予定終了日を超えない |

   ```bash
   node scripts/notion.mjs task-create --project $1 --parent TSK-000 \
     --name "1-1. 保管先の接続実装" --estimate 8 --kind 開発 --priority 高
   ```

9. 登録前に、親ごとにまとめた一覧を表で示す。列は タスク名、工数区分、見積工数h、優先度、担当者、期日 とし、親ごとと全体の合計工数も出す。
10. **利用者の確認を取ってから** 登録する。
11. 登録後、親と子の構造、合計工数を報告し、次に `/task-pr TSK-000` を実行できることを伝える。

## 注意

- 優先度は登録の数秒後に Notion のオートメーションが `中` へ戻す。`--priority` の指定は残らない。残したい場合だけ `NOTION_VERIFY_DELAY_MS=8000` を付けて実行する。1 件あたり 10 秒前後かかる。
- 見積の合計がプロジェクトの `予想開発時間` と大きくずれる場合は、登録前に指摘する。
- 1 つの親に子が 6 件を超える場合は、親の分け方を見直す。
- ステータスは既定の `未着手` のままにする。着手時に `/task-pr` が更新する。
