argument-hint: <PR 番号 | 省略時は今のブランチの差分>
allowed-tools: Read, Glob, Grep, Bash(git diff:*), Bash(git log:*), Bash(git fetch:*), Bash(git show:*), Bash(git grep:*), Bash(git branch:*), Bash(gh pr view:*), Bash(gh pr diff:*), Bash(gh repo view:*)

PR `$1` をレビューする。観点の選び方、指摘の書き方、見た範囲の示し方は [rules/review.md](../../rules/review.md) に従う。

レビューでは読むだけにする。コードもファイルも直さず、PR へのコメントも、利用者に頼まれるまで書かない。

## 手順

### 1. 対象を集める

1. `gh pr view $1` で PR の本文、タイトル、マージ先のブランチを、`gh pr diff $1` で差分を読む。
   `$1` が省略された場合は、今のブランチの PR を `gh pr view --json number,baseRefName` で探す。PR が無ければ、`gh repo view --json defaultBranchRef` で既定のブランチ（案件のリポジトリでは `dev`）を調べ、そのブランチとの差分を対象にする。`main` と決め打ちしない。
2. PR の変更後のファイルを読めるようにする。今のブランチが PR のブランチで、リモートと同じなら、手元のファイルをそのまま読む。そうでなければ `git fetch origin pull/$1/head:review-$1` で取り込み、`git show review-$1:<パス>` で読み、`git grep <語> review-$1` で参照を探す。手元のファイルを PR の内容として読まない。
3. 変えたファイルを一覧にする。差分だけで判断せず、変えたファイルの前後と、変えたファイルを参照している場所も読む。

### 2. 当てるルールを決める

4. [rules/review.md](../../rules/review.md) の「観点の選び方」に従い、当てるルールを決める。変えたファイルごとに、[rules/README.md](../../rules/README.md) の「読む場面」を見て選ぶ。
5. 選んだルールのファイルを開いて読む。覚えている内容で済ませない。

### 3. 見る

6. 当てたルールの「必須」と「推奨」の項目ごとに、差分が守っているかを見る。
7. 横断の観点（正しさ、エラーと境界、セキュリティ、テスト、重複とずれ、消えたもの、読みやすさ）を 1 つずつ見る。
   - 正しさは、手順やルールなら実際にその順に進めてみて、矛盾や行き止まりがないかを確かめる。
   - 消えたものは、削除された行が別の場所に移っているかを検索して確かめる。
8. 指摘の候補は、PR の変更後のファイルを読み直して確かめてから残す。確かめられないものは「未確認」とする。

### 4. まとめる

9. 指摘を重い順に並べ、指摘ごとに重さ、問題、起きること、修正案、根拠のルールを書く。
10. 最後に、見た範囲の表を出す。

   | 観点 | 根拠 | 結果 |
   | --- | --- | --- |
   | Git と Pull Request | rules/git.md | 指摘あり（1 件） |
   | 正しさ | rules/review.md | 問題なし |
   | テスト | rules/review.md | 該当なし（文書だけの変更） |

11. 直すかどうかは利用者に聞く。

## 注意

- このコマンドの名前は、Claude Code に最初からある `/review` と重ならないよう `/rule-review` にしている。
- `git fetch` で作った `review-<番号>` のブランチは、レビューが終わったら `git branch -D review-<番号>` で消してよい。
- 正しさの観点で、コードのバグを深く探したいときは、Claude Code の `/code-review` を併用してよい。その結果も、この手順の重さと見た範囲の表に入れ直して示す。
